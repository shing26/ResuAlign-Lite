## 三、67 个「整轮硬阻断」的真实机制（复核）

`api/services/alignment_rules.py::split_verified_diffs`：evaluator 判「本轮有
无依据内容」但**没给出具体 diff id** 时，按 ADR-0019 回退**整轮硬阻断**——
所有建议一起作废。

抽样 177 条被拦建议逐条核对：
- 26 条（15%）直接命中 `missing_keywords` → 门禁正确
- 其余明细项是 `UseG1GC / TCC / Seata / B+Tree / NIO / Alibaba` 这类简历里
  确实没有的术语 → **门禁正确**
- 疑似误拦（术语其实在简历里）: **0**

**结论：这不是误拦，是粗粒度否决。** 安全上没错，代价是 29% 的对齐运行
归零。改它需要动 ADR-0019 的硬门语义（上游 truetailor 优先），属产品安全
决策，不该由执行者单方面放宽。

## 四、真正的产品缺陷（已修，2026-10-26）

抽样 22 个「可用」岗位的建议正文，发现 **45%（18/40）的建议正文里混着系统
占位符模板**：

```
- 后端工程深度：熟练 Java 21 虚拟线程 …，支撑 AI 应用后端服务。
  [待人工确认：耗时降低 X% / 支撑 QPS 达 Y]
```

成因：`engine/tailor.py::_ensure_metric_placeholder` 把「指标待补」提醒
**直接拼进 `proposed`**，而 `proposed` 会成为简历正文。用户看到这种正文
自然不会采纳——于是 22 个可用建议只采纳了 3 个。

**修复**：
1. 提醒改落 `reason`（卡片可见），`proposed` 保持干净 —— `_note_metric_confirmation`
2. `_apply_diffs` 采纳时剥离历史占位串（老建议也能直接用）
3. API 投影剥离历史占位串（19 个未采纳岗位立刻变干净）
4. 实测：真实库 40 条可用建议，带占位串 18 → **0**

## 七、关于「一直改但没成效」

诚实结论：本会话及之前的 UI / CSS 结构债 / CI 门禁 / 词表扩充，**没有一条
改善了上面的漏斗**。它们提升的是工程质量与界面一致性，而漏斗断在
「对齐成功率」和「建议可采纳性」上。

本次修的是第二处断点的直接原因（占位符污染）——这是**第一个真正作用于
成效数字**的改动。第一处断点（成功率）主要受额度（78 例）和编辑器质量影响，
两者都需要资源投入或产品决策。

## 八、P2 实测记录（2026-10-26，本地 8000，零 LLM 调用）

在 22 个「可用建议」岗位上实跑「采纳→定稿→导出」，又发现两个卡点并修复
（PR #193）：

1. **历史建议看得见、无法采纳**：`accept` 只从内存 job registry 取建议，
   旧运行过期即 404 —— 19 个岗位全部命中。已改为回退持久化 `diffs_json`。
2. **占位串投影只覆盖一半路径**：`/api/jobs` 与 `/api/jobs/{id}` 仍返回
   带占位串的建议（实测 6 个岗位残留 10 处）。已统一到
   `services/alignment_rules.py::strip_placeholders_in_diffs`，残留归零。

**链路实测结果**：2 个岗位走通 accept → 草稿（无占位串）→ 定稿 v1 →
Markdown 导出（含模型/生成版本/匹配分溯源元数据）。

**数据现实（决定下一步）**：

| 观察 | 数字 |
|---|---|
| 未定稿的可用建议岗位 | 19 个 |
| 其中钉住的简历已被删除（建议成孤儿） | **11 个** |
| 剩余岗位里建议锚点仍可应用 | 9/12 = **75%** |

结论：**旧运行撑不起自用线**（简历已改版/简历被删），必须在当前简历上
重跑对齐；而重跑的直接障碍是额度（78 例失败为欠费）。因此下一步顺序为：
额度修复（用户）→ 3 份真实 JD 重跑 + 走完采纳/定稿/导出（可陪同）。
