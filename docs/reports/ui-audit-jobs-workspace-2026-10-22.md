## 1. 岗位库（kanban）

### J1 [P0] 卡片标题被压成逐字竖排；根因是顶行 5 个控件挤在 179px 里（已在工作区修复，未提交）

**证据（改动前）**
- `desktop-jobs.png` 第 1 列首卡：标题"产品经理（2027 届秋季校招·普通批）"一字一行，卡片高 550px；同页第 2 张"后台开发"同样竖排。`mobile-jobs.png` 更严重。
- 实测 1440：卡片 205.2px 宽，`.board-card__top` 内容宽 179.2px，5 个子项实测 `board-check 24 / match-badge 42 / title 25.2 / reveal-toggle 28 / board-more 28` + 4×8px gap = 179.2px；标题 `clientWidth 25.2`（< 2×13px 字号）→ 每行 1 字，`titleLines 15`、高 292.5px；移动端标题只有 14px 宽、16 行、312px 高，卡片最高 2,802px。
- 同页 `.match-badge` 的"待分析"也被压成 2 行（42×38.8）。

**用户影响**：第一屏的卡片长成一列「中文竖排」，任何人第一眼都会判定"这页坏了"。

**根因**
- `.board-card__top`（`styles.css:3422-3426`）是单行 `display:flex; flex-wrap:nowrap`，塞了复选框+匹配徽标+标题+展开箭头+更多菜单 5 个控件。
- `.board-card__title`（`styles.css:3428-3438`）只有 `flex: 0 1 auto` + `min-width:0`，是唯一可压缩项；其余 4 项固定（24/42/28/28）。可用空间 179.2 减去固定 154 只剩 25.2px，中文 min-content = 1 个字号宽，于是逐字换行。
- 匹配徽标同理被 `min-width:42px` 夹住的最小宽度撑成两行。

**改法建议**：顶行只留「复选框 + 标题(2 行 clamp) + 更多」；匹配徽标/展开箭头下移到元信息行，元信息单行省略；标题加 `title` 全量。工作区里已按这个方向改完（`.board-card__top` 新块 `styles.css:9118-9145`，`format.js:1245-1258`）。

**改动后复测**：标题 111.2×39px（2 行、clamp 生效），卡片 230.5px、整列卡片等高；列内滚动 180,603 → 71,097px。**残留 3 点**：① 元信息 `.board-card__meta-text` 有省略号但**没有 title 属性**，公司/城市/薪资被截断后无处可查（`format.js:1252`）；② 移动端标题只剩 100px（复选框触摸区 32px），仍只能读 2×7 字；③ `title` 提示在触屏上无效，长标题在手机上始终不可全读——建议长按/点标题进工作台（已有）+ 工作台头部完整显示（见 W2）。

**预估工时**：主体已做；残留 0.5 h（meta title + 移动端腾出标题宽度）。

### J2 [P0] 看板几何与数据分布不匹配：317 张卡挤在 223px 单列，4 个空列白占 893px，要滚 121 屏

**证据**
- 实测 5 列各 **223.2px**；列内卡片数 `317 / 1 / 0 / 0 / 0`；看板总宽 1164px → 4 个空列占 **892.8px（76.7%）**。
- `未投递` 列 `.board-col-body` 内容高 **71,097px**、视口 **587px**（每屏约 2.5 张卡）→ 从顶滚到底约 **121 屏**（改动前 180,603px ≈ 308 屏）。移动端该列 163,093px。
- 规则出处：`.board-column` `flex:1 1 220px; max-width:320px; min-width:220px`（`styles.css:7757-7768`），5 列由 `kanban.js:78-95` 固定生成，没有任何按数量折叠/扩列逻辑；列高交给 `.board-col-body { overflow-y:auto }`（`styles.css:7807-7813`）。
- 空列渲染"暂无岗位"虚线框（`styles.css:7893-7900`，实测 3~4 个）。

**用户影响**：1440 显示器上 3/4 的横向空间在说"这里没东西"，唯一的 317 条数据被塞在 220px 宽、要滚 121 屏的细条里——用户根本不知道从哪开始翻。

**根因**：看板固定 5 等分列，且把"看板列"当唯一浏览形态；数据分布（317:1:0:0:0）与 5 列等分的几何完全脱钩。

**改法建议**（按成本递增，可分批）
1. 空列折叠：`count===0` 的列渲染成 56–72px 竖条（竖排标签+0 徽标），非空列 `flex: 2 1 320px`；纯 CSS + 一个 `has-cards` 类，30 min。
2. 给岗位库加「看板 / 列表」视图开关（默认列表）：列表 = 单列行卡（标题+公司+状态徽标+匹配分+操作），317 行可扫；看板保留给投递阶段管理。1.5–2 h。
3. 若坚持看板：非空列内加「显示更多 / 只看待处理」，首屏只渲染 20 条（见 J7）。

**预估工时**：方案 1 ≈ 0.5 h；方案 2 ≈ 2 h；建议 1+2 一起（2.5 h）。

### J3 [P0] 卡片的「工作状态」全部藏在折叠区：209 个对齐失败在列表上完全不可见

**证据**
- `format.js:1255-1271`：`alignmentBadgeHtml`（已对齐/对齐失败/无缺口）、缺口、定稿版本、投递时间、截止日期全部在 `.board-card__reveal` 里；`styles.css:7837 / 7848` 决定它默认 `display:none`，桌面实测 `revealDisplay: none`。
- 折叠态可见的只有：匹配徽标、公司/城市/薪资、`去投递`、状态 select、`开始对齐/重新对齐`、`工作台`。**没有任何一个字节说明这个岗位"对齐过没有、成功没有"**；失败岗位只能从按钮文案"重新对齐"反推。
- `/api/jobs?limit=500` 实测分布：`alignment_status=failed` **209**、`succeeded` 22、无 `jd_profile` **87**（`idle` 87）；而看板列按投递状态分，317/318 都落在"未投递"一列——用户关心的"哪 22 个能直接用、哪 209 个要重跑、哪 87 个还没分析"在页面上一格都没有。
- 头部转化条只有"投递转化 0%（1/318）/ 面试转化 0%（0/1）"（`kanban.js:104-107`），也没有工作状态口径。

**用户影响**：岗位库回答了"我投到哪一步"，但没回答"我该先处理哪个"；318 条里 209 条失败、22 条有产出，用户只能逐张点开 317 次才知道谁是谁。这是本页"无从下手"的直接原因。

**根因**：卡片信息架构把"投递阶段"当唯一维度；对齐结果被降级为详情（reveal），而看板列又按投递阶段切分，导致"工作状态"在页面没有任何承载体。

**改法建议**
1. 把 `alignmentBadgeHtml`（或至少一个语义色点 + 短文案）提升到卡片 meta 行，与匹配徽标并列；失败=红点、已对齐=绿点、待分析=灰点。0.5 h。
2. 工具条加「工作状态」分段筛选：全部 / 待分析 / 已对齐 / 对齐失败 / 已定稿，前端对 `state.jobs` 过滤即可（不依赖后端）。0.5–1 h。
3. （可选，与 J2 方案 2 合并）列表视图默认按工作状态分组。

**预估工时**：1+2 ≈ 1.5–2 h（含 3 种状态窄屏样式与空态）；含列表视图 ≈ 3.5 h。

### J4 [P1] 每张卡 14 个可交互目标、6+ 条重复入口；「开始对齐」一点就直接花 LLM 的钱

**证据**
- 实测单卡 14 个可交互元素：`checkbox`、标题（打开工作台）、展开箭头、更多菜单（+4 项：安排跟进/详情/编辑/删除）、`去投递`、`分类待定`（重新分类）、状态 `select`、`开始对齐`、`工作台`。全页 **3,131 button + 325 select**；纯键盘 Tab 走一遍 ≈ 14×318 ≈ **4,452 站**。
- 代码：`format.js:1245-1282`（卡片主体）、`1284-1296 boardAlignButton`、`1058-1070 boardMoreMenu`；`去投递` 按钮来自 `format.js:2242-2246`。
- 关键：`main.js:2275-2301` 的 `align-job` **无任何确认**，直接用 `/api/master-resumes?limit=1` 拿"最近一份简历"+ 固定 `medium` 粒度 POST `/api/.../workbench`，立刻排队一次真实对齐；按钮文案是"开始对齐"（新手最容易点的那个）。当前数据里 87 张卡（`alignment_status=idle`）显示"开始对齐"、209 张显示"重新对齐"（`/api/jobs` 实测分布）。
- 功能重复：`标题` 和 `工作台` 都调 `open-optimizer`；`开始对齐` 与 `批量对齐`、`一键预分析` 又构成三条"让它跑"的路径。

**用户影响**：卡片像一整块控制面板，不是"一张岗位卡"；用户想点进去看，却误触"开始对齐"，花一次钱、用的还是系统替他挑的简历。

**根因**：操作平铺（每个功能一个按钮），没有主次与收纳；`align-job` 缺"用哪份简历/什么粒度/大概多久"的前置确认。

**改法建议**
1. 卡片操作收成「1 主操作 + kebab」：主操作=打开工作台（查看/继续）；kebab 收纳 开始对齐 / 去投递 / 编辑 / 详情 / 安排跟进 / 记录投递 / 重新分类 / 删除。
2. `开始对齐` 改成两步：先弹轻确认（选择主简历 + 粒度 + 提示"将调用一次 AI 对齐，约 1–3 分钟"），确认后才 POST；或直接把按钮改成"去工作台运行"。
3. 状态迁移只保留 select；批量复选框只在"批量模式"下显示（同时解决移动端标题宽度，见 J1 残留）。
4. 去掉重复的"工作台"按钮（标题已承担）。

**预估工时**：2 h（含确认弹层复用 `showModal`；不含 LLM 行为改动）。

### J5 [P1] 「一键预分析 / 批量对齐」没有数量与代价提示；当前一键预分析 = 87 岗 × 2 次 LLM

**证据**
- 按钮：`kanban.js:132-144`（`一键预分析` / `批量对齐` / `添加岗位` / `数据`）。
- `一键预分析` → `main.js:1540-1582` → `POST /api/jobs/preanalyze-pending`；服务端 `api/services/jobs.py:1233-1239` 收集所有"待预分析"岗位（`job_needs_preanalyze`，上限 `_MAX_PREANALYZE_BATCH=200`，`jobs.py:1216`），当前实测 **87 个**（`classification_pending=87`），代码注释实测每岗 2 次串行 LLM 调用、约 3.5 s/岗 → 一次点击 ≈ 87×2 次调用、**5 分钟以上**。
- `批量对齐`（`main.js:2583-2605`）直接把 `selector:"pending"` 全部排队后才打开面板，用户看到"已排队 N 个"时已经提交了。

**用户影响**：两个最显眼的按钮都是"批量花钱/批量等"，但文案里没有数量、没有预计时长、没有"会分析全部 87 个岗位"的提示；用户要么不敢点，要么点完才发现搞大了。

**根因**：批量动作的前端文案是静态的、提交前不查询"将处理多少"（数量只有后端在 POST 后才返回）；按钮与"实际代价"之间没有确认环节。

**改法建议**：按钮文案带计数（`预分析待处理（87）`）；点击先 `showModal` 列出"将处理 N 个岗位 · 预计 X 分钟 · 可随时停止"，确认后再发；结果面板里给出"停止"（预分析已有，批量对齐也有取消，复用即可）。

**预估工时**：0.5–1 h。

### J6 [P1] 筛选零结果 ≠ 空库：仍显示「还没有岗位」整卡引导 + 5 个「暂无岗位」空列，且没有"清除筛选"

**证据**
- `kanban.js:100`：`const emptyGuide = state.jobs.length === 0 ? jobsEmptyGuideHtml() : ""` —— 用的是**过滤后**的列表长度，不是库是否为空。
- 实测（筛选 `search=zzz-no-such-job-zzz`，纯 GET）：卡片 0、引导卡文案「还没有岗位 / 粘贴一份 JD 或导入收藏链接开始」、5 列全部「暂无岗位」、转化条变成 `投递转化 —（0/0）`——而库里实际有 **318** 条。整页从上到下是：三步引导（约 200px）→ 转化条 → 工具条 → 大号"还没有岗位"空态 → 5 个空列，约 570px 的空内容。
- 没有"当前位置：筛选结果为空 / 清除筛选"的列表级空态；用户只能重新展开筛选→点清除。

**用户影响**：随手筛一个条件没结果，页面就说"你还没有岗位"，用户会以为 318 条数据没了；而真正的恢复动作（清除筛选）还藏在收起的筛选面板里。

**根因**：只实现了"库级空态"（`jobsEmptyGuideHtml`），把它复用成"列表级空态"；未区分 `state.jobs.length===0` 与"有筛选条件但结果为 0"。

**改法建议**：新增列表级空态：`hasActiveFilters()` 为真时渲染「没有匹配的岗位 · 关键词/职能/级别 ×」并把「清除筛选」做成主按钮；库真空才渲染 onboarding 引导；转化条在筛选态显示"筛选后 0 条（库内 318）"。同时把"筛选"按钮加一个激活态徽标（当前打开/已生效），否则用户不知道筛选为什么在生效。

**预估工时**：0.5–1 h。

### J7 [P2] 318 张卡全量渲染：20k 节点、3,131 个按钮、325 个 select，没有窗口化或分页

**证据**
- 实测：DOM **20,472** 节点、**3,131** button、**325** select、318 个 `.board-card` 全部在 DOM。census 独立测到 20,147 / 3,129，可互相印证。
- 时间：到 318 卡可见 **0.8–1.0 s**（3 次复测）；改动前抓到过 543 ms 长任务，当前 53–150 ms —— 所以"慢"目前不是主要痛点，**节点/控件数量与 500 条截断才是**。若数据涨到 1,000+ 条，本项升级为 P1。
- `kanban.js:67-76` 一次 `GET /api/jobs?limit=500` 后 `items.map(boardCard).join("")` 全量拼 HTML（**limit=500 且无"已截断"提示**，超过 500 条时会静默丢数据）；每张卡还内嵌 1 个 `<details>` 菜单（4 个按钮）和 1 个状态 `<select>`（5 项），即使折叠也在 DOM 里。

**用户影响**：页面本身还能用，但 20k 节点 + 4,452 个键盘 Tab 站让滚动/辅助技术都变重；数据超过 500 条会"消失"，用户不会被告知。

**根因**：无虚拟列表、无分页、无懒渲染；卡片模板把详情/菜单/下拉全塞进初始 HTML。

### W8 [P1] 移动端：双栏切换器被后置 CSS 覆盖成 `display:none`，整页变成 4,425px 单列，右栏在 2,977px 处

**证据**
- 移动实测（改动后）：`.wb-mobile-tabs` 尺寸 **0×0**、computed `display:none`，Playwright 点「调优」报 `element is not visible`（30s 超时）；`.wb-context` 218→522（高 304）、失败横幅 534→632、`.wb-main` 从 632 起高 **2,346px**、`.wb-aux` 从 **y=2977** 开始、文档高 **4,425px**（5.2 屏）。
- CSS 冲突：`styles.css:8860`（`@media(max-width:900px){ .wb-mobile-tabs{display:flex} }`）被 `styles.css:10413-10435` **同断点、同优先级、更靠后**的 `.wb-mobile-tabs{display:none}` 覆盖；`split-canvas.js:277-280` 的「调优 / 结果」分段按钮与 `state.wbMobilePane` 因此完全失效。
- 而 `.split-layout .split-pane[data-wb-pane="diff"].is-active` 那套互斥规则（`styles.css:6707-6724`）只作用于老的 `.split-canvas/.split-pane`，当前的 `.wb-main/.wb-aux` 没有窄屏互斥规则 → 两栏永远上下堆叠。

**用户影响**：手机上先过 218px 全局头 + 304px 岗位头 + 98px 红色横幅（**首屏 75%（632px）被头部吃掉**）才看到"简历精修"；想改主简历/看岗位分析要滚 3.5 屏；设计好的 tab 根本点不到。

**根因**：CSS 双写冲突（后置规则覆盖）；窄屏 pane 互斥只在旧类名上实现过。

**改法建议**：① 删掉 `styles.css:10432-10434` 对 `.wb-mobile-tabs` 的 `display:none`（保留 `.wb-tabs` 吸顶那条）；② 窄屏按 `is-active`/`data-mobile-pane` 给 `.wb-main`、`.wb-aux` 加 `display` 互斥（参照 6714-6720 的旧规则）；③ 或更省事：不信 tab，改为「结果 | 调优」两个锚点按钮，把 aux 的三个 pane 做手风琴放在 diff 列表后。

**预估工时**：1.5–2 h（含回归截图）。

### W9 [P2] 移动端工作台首屏没有任何可操作内容；失败横幅是唯一 CTA

**证据**：移动截图 `postfix-ws-mobile.png` + 实测：0-218 全局头（页面标题/浅色/搜索），218-522 岗位头（标题+公司+技能 tags+统计+切换 select+去投递/记录投递），534-632 失败横幅，632 起「简历精修」标题（652-752）+ 指标条（767-835），**第一张建议卡 y=851、高 733px**——首屏 844px 的下沿刚好把它全部挡在下面。`split-canvas.js:272-274` 底栏动作条只在 failed/running 启用，这里没有底栏。

**用户影响**：手机打开工作台，满屏是标题、元信息、技能标签和一段红字，没有任何"下一步"按钮；用户只能靠直觉往下滑两屏。

**根因**：窄屏把桌面头部整块纵向堆叠（`.wb-context { flex-direction: column }`，`styles.css:8835-8840`），没有为窄屏裁剪信息层级；底栏动作条 `barActive`（`split-canvas.js:272-274`）只认 failed/running，不认"有被拦截建议可查看"这种可行动状态。

**改法建议**：移动端头部折叠成「岗位名 + 一行 meta + 状态徽标」，公司详情/技能 tags/统计/切换收进「详情」折叠；失败横幅下直接给「查看被拦截建议（3）」锚到列表；将主 CTA 固定在底部（复用现有 `.wb-action-bar`，把 `barActive` 扩展到"有可查看的被拦截建议"）。

**预估工时**：1 h。

## 4. Top3 最该先修

1. **J3 卡片的「工作状态」不可见（P0）** —— 318 条数据里 209 失败 / 22 已对齐 / 87 待分析，但看板、卡片折叠态、头部指标没有一处承载"工作状态"；用户连"该处理哪个"都没有入口，这是"无从下手"的直接根因，而改法只是"把已有徽标提到可见行 + 一个前端筛选"，1.5–2 h，收益最大。
2. **W1 失败态同一句话出现 6 次 + 0 建议 / 3 张卡自相矛盾（P1）** —— 用户当前真实打开的就是失败页（209/318 失败），第一眼是满屏重复红字与互相打脸的指标，观感等同于"坏了"；统一信息源 + 失败摘要卡 1–1.5 h 就能把失败页从"看不懂"变成"知道下一步"。
