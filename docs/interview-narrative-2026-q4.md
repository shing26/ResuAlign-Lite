## 2. 三段式口述叙事（60–90 秒）

**第一段 · 问题与立场**：LLM 改简历的唯一不可接受失败是编造事实——编造会在
面试里穿帮。所以我不做「更聪明的改写」，做「每条改写必须指回原文、过不了门禁
就拦截」的受控生成架构，且门禁是 fail-closed：解析不出 provenance 就拦截，不
放行。

**第二段 · 数据打脸与归因**（区分度所在）：上线后真实复测发现 4/5 零产出，且
少数「可用」案例是 allowlist 语义缺陷放行的编造——不是模型造假，是我的护栏把
「JD 要求但简历没有的词」当成了改写许可。我拆了字段语义（supported vs missing）、
加了三层防线、复测，每一轮数字都记在仓库里。这段证明的是：我有拆穿自己产品的
习惯和归因能力。

**第三段 · 现状与边界**：核心可用率仍未达标（自用 0/3），评估体系缺真实接受率
数据——两者都在当前打磨计划里，计划是预注册的。我不宣称它是个好产品；我宣称
它是一次带完整仪表盘的可靠性工程实验。

## 3. 预答追问

**Q：你自己用它拿到 offer 了吗？**
A：还没有，这是我项目最大的未验证假设——自用线 0/3，我把它作为红线公开在
STATUS.md。当前秋招期的每次重点投递都会走完整工作台闭环，1 月前会有第一批真实
数据。我更愿意用未验证换诚实，而不是编一个使用故事。

**Q：为什么没有 Agent 循环 / 多 Agent 协同？**
A：我有一个机械判据：某步若在 30 次重放里能被一条确定性规则复现，它就不是决策
点，不该上循环。实测我的管线里没有真正的决策点，所以我做了预设流 + 单入口路由，
并建了一套离线判卷 harness（tools 臂 vs template 臂、9 个违规注入器）来回答
「循环协议能不能被模型满足」——先建评测，再决定架构。为凑「Agent」关键词上循环
是我明确拒绝的。

**Q：可用率为什么这么低？根因是什么？**
A：三层：① allowlist 语义错误把 JD 缺口词当改写许可（已修，ADR-0060/0061）；
② 编辑器单发可达 170s、墙钟是硬截止（已放宽到 150s 并实测，ADR-0062）；
③ 剩余瓶颈是编辑器证据化不足——「无安全改写」被正确分型为合法终态，不是 bug。
前两类是工程问题已解决；第三类是能力边界，我不打算用编造来填。

**Q：和直接用 ChatGPT/Kimi 改简历有什么区别？**
A：通用模型是「生成」，无法承诺不编造；我的系统是「受控生成 + 确定性校验」：
每条建议可指回原文，编造候选被拦截而不是被相信。对抗用例下 8/8 编造被拦截。
另外它是本地优先的——简历和 JD 不出本机，API Key 落盘加密。

**Q：为什么字节级 vendor 锁？67 个 ADR 是不是过度工程？**
A：vendor 锁解决一个真实问题：同一套门禁规则跑在 app 和 Claude Code/Codex skill
两个形态里，没有哈希清单和对拍测试，两边会静默漂移。ADR 每个都由真实事故触发
（比如 0060–0062 是同一次假通过事故的直接产物），不是仪式。简历上我只放可复现
的工程数字，治理细节留给追问。

**Q：单机 SQLite 工具为什么做熔断/watchdog/成本护栏？**
A：因为 LLM 依赖是外部不稳定源：节点会超时、鉴权会失效、账单会失控。熔断
（连续 3 次失败自动隔离 + 恢复路径）、watchdog（1800s 墙钟，条件 UPDATE 防迟到
写入）、cost_guard（每日上限 + 连续失败熔断）都是针对这个依赖面的，不是给
SQLite 用的。故障注入 5/5 恰第 3 次熔断可复现。

**Q：上下文工程做了什么？**
A：三个可讲的点：① 两阶段抽取（启发式缩小范围 → LLM 精修，省 60–80% token）；
② JD 上下文边界——一次真实事故发现模型把 JD 上下文当编造许可，于是改为 ≤300
字结构化摘要、永不进 allowlist（ADR-0061）；③ 不可变版本 + append-only 快照，
「遗忘」靠指向不变历史而不是删除。

## 4. 面试材料策略

- **不做 live demo**：编辑器单发可达 170s，现场冷场风险高。用 README 的
  before-after SVG（输入/判定都来自仓库）+ 需要时补一段录屏。
- 30 秒版入口：skill 仓 truetailor（零安装，SKILL.md + stdlib 门禁脚本），
  适合「扫码就看」的场景。
- **每场面试后**在本文档追加：被问住的问题、叙事哪段失效、对方追问的深水区。
