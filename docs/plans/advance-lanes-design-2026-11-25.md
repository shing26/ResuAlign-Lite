## 0. 先更正一处数字

上一轮口头汇报说的「11 月导入 116 个岗位全部未分析」，把两件事混在了一起。
按现有谓词拆开后（已剔除 168 行测试夹具：标题为 `B` / `对齐0` 等、JD ≤ 20 字）：

| 桶 | 定义 | 数量 |
| --- | --- | ---: |
| ① 待预分析 | `idle` 且无 `jd_profile` | **65** |
| ② 已预分析 · 未对齐 | `idle` 且有 `jd_profile` | **152** |
| ③ 待定稿 | `succeeded` 且 `usable_diffs≥1` 且无定稿 | **17** |
| ④ 对齐失败 | `failed` | **207** |
| ⑤ 已定稿 | `final_draft_version≥1` | **8** |
| 合计 | | **449** |

65 + 152 + 17 + 207 + 8 = 449，与真实岗位总数**严格相等**，五桶互斥。
「116」是 11 月新增岗位总数，其中 65 未预分析、51 已预分析但没跑对齐。

## 1. 要解决的问题

两个独立但同源的断点：

1. **职位页只按「投递状态」组织**，没有「下一步做什么」的维度。17 个已经产出可用
   建议、只差一次采纳的岗位，和 207 个失败岗位、152 个待对齐岗位混在同一张列表里，
   只能靠人肉翻。
2. **驾驶舱「继续」选不到它们**。`dashboard.py` 取的是
   `updated_at DESC` 的第一条非 `succeeded`；而待定稿岗位的
   `alignment_status` 恰好是 `succeeded`，被这条规则直接跳过。结果是 11-23 刚导入
   的空岗位永远排在前面。

数据佐证：真实投递 1 条，但**有可用建议 25 条、已保存定稿仅 8 条**。
中间 17 条不是「没产出」，是**产出后没有落点**。

## 2. 方案 A：职位页「待推进」分组条

### 2.1 形态

在页面标题与搜索行之间插入一条分段条，五段互斥、各带数量：

| 段 | 文案 | 数量 | 副标题 | 主色 |
| --- | --- | ---: | --- | --- |
| ① | 有建议 · 待定稿 | 17 | 已跑完对齐，差你采纳 | accent |
| ② | 未预分析 | 65 | 导入后还没跑过 | 中性 |
| ③ | 已预分析 · 未对齐 | 152 | 有 JD 画像，没生成建议 | warn |
| ④ | 对齐失败 | 207 | 零产出 / 额度 / 服务错误 | danger |
| ⑤ | 已定稿 | 8 | 可直接导出或记录投递 | 中性（弱化） |

- 默认**不选中任何段** = 当前行为（全部）。
- 选中段后，列表只显示该段；段下方出现一行说明条，写清「正在看什么 + 该做什么」。
- 段顺序按**离完成由近到远**排：①→②→③→④→⑤。不按数量排，因为这里要回答的是
  「先做哪个」，不是「哪个多」。

### 2.2 为什么不是再加一排 chip

看板视图已有一排「全部 / 待分析 / 已对齐 / 对齐失败 / 已定稿」。如果分组条另起一套，
就是 ADR-0069 明确要消除的「两套并行筛选」。

**决定：分组条与看板 chip 共用同一个状态**，键名统一为 `advance`：

| 旧 key | 旧语义 | 新 key | 变化 |
| --- | --- | --- | --- |
| `all` | 全部 | `all` | 不变 |
| `pending` | 所有 `idle` | 拆成 `unanalyzed` / `unaligned` | **一拆二** |
| `aligned` | `usable≥1`（含已定稿） | 拆成 `pending_draft` / `finalized` | **一拆二** |
| `failed` | `failed` | `failed` | 不变 |
| `final` | 有定稿 | `finalized` | 合并进上一条 |

拆分的理由：`aligned=25` 里混着 8 个已定稿，把「已经做完」和「差你一步」放在一起，
正是当前最误导人的地方。

### 2.3 计数必须来自服务端（关键正确性约束）

**不能在前端数。** 列表只加载 `limit=500` 并按 `updated_at` 排序；实测 17 个待定稿
岗位里有 7 个落在第 500 条之后。前端计数会显示 10，点进去也只有 10 条。

因此两条都必须服务端化：

1. **筛选**：`GET /api/jobs?advance=<bucket>`，在 SQL 里过滤**再**分页。
2. **计数**：五桶计数由服务端聚合，不依赖当前页。

计数落点有两个选择：

- **A（推荐）** 扩展现有 `GET /api/dashboard`，加 `advance` 字段。
  `job-hall.js` 已经在调这个接口（`hall.dashboard.kpi.jobs` 就是「全部岗位」的来源），
  零新增请求、零新增失败面。
- **B** 新增 `GET /api/jobs/advance-summary`。隔离更干净，但多一次往返。

选 A：语义本来就是「租户级聚合」，且能复用已有的降级路径（dashboard 失败不影响列表）。

### 2.4 谓词只允许有一份

后端已有 `api/services/jobs.py::job_needs_preanalyze`，是「一键预分析」的唯一跳过
谓词。分组条必须复用它，**不能在 SQL 里另写一套**。

做法：

- 把五桶判定抽成 `advance_bucket(job) -> str`，纯 Python，复用 `job_needs_preanalyze`；
- SQL 侧写等价的 `CASE WHEN`（列表筛选必需）；
- 加一条 parity 测试：对同一批夹具，Python 分桶结果 == SQL 分桶结果，逐条比对。
  这是防止两套谓词漂移的唯一手段（同 `gate.py` 与 `tailor.py` 的 parity 做法）。

### 2.5 与现有筛选的组合

- 分组条是**导航**，不是筛选条件：计数永远是全库口径。
- 与搜索/城市/招聘类型**取交集**：选中「待定稿」再搜「Java」，列表显示交集中的条目，
  列表头写实际条数（如「3 个岗位」），段上的 17 不变。
- URL 可深链：`#/jobs?advance=pending_draft`，与既有 `?status=` / `?view=` 同风格。
- 移动端 390：2×2 栅格 + 第 ⑤ 段整行弱化，不出现「孤零零一格」。

## 3. 方案 B：驾驶舱「继续」按完成度优先

### 3.1 排序规则

```
优先级 1  待定稿      succeeded ∧ usable_diffs≥1 ∧ final_draft_version=0
优先级 2  未预分析    idle ∧ job_needs_preanalyze
优先级 3  已预分析未对齐 idle ∧ has profile
优先级 4  对齐失败    failed
```

同一档内：`match_score DESC`（无分视为 0）→ `updated_at DESC`。
四档全空时，退回当前行为（取最近更新的一条）。

### 3.2 为什么优先级 1 必须排最前

它是**唯一一个「再走一步就完成」的状态**：建议已生成、已过真实性检查，只差用户点
采纳并保存。排在其他任何状态后面，等于让最接近完成的工作永远排在队尾。

### 3.3 需要的改动点

- `job_library/__init__.py::list_dashboard_jobs` 的 SELECT **缺少两列**：
  `final_draft_version`（判优先级 1）与 `match_score`（档内排序）。两列都要补。
- `api/routers/dashboard.py::get_dashboard` 的选取循环改为按上述优先级。
- `DashboardQuickContinue` 增加 `next_action` 字段（枚举四值），供前端决定徽标与
  按钮文案；纯增量，不改既有字段。
- `dashboard-view.js` 按 `next_action` 渲染：
  待定稿 → 「待定稿」徽标 + 主按钮「审建议」；其余保持现有文案。

### 3.4 保持单卡，不做三行列表

预览图右侧画的是三行「接着做」，但那属于 P2 的体验增强。本轮只改**选谁**，
不改卡片形态——卡片从 1 行变 3 行会牵动移动端高度与既有快照测试，收益不成比例。
浏览面由职位页的分组条承担。

## 4. 不做什么

- 不改 `library_jobs` 表结构，不加持久列。五桶全部由现有列派生。
- 不改模型、不改编辑器、不碰 `gate.py` / vendor fixtures / 对齐链路。
- 不做「一键批量采纳」。17 条建议需要人看，批量采纳会把「代点等于自证」的问题
  从测试脚本搬进产品。
- 不动导航命名、评分图形、首页样例（ADR-0059 P4 范围）。
