# ADR-0053: 用户主动解冻架构加固挂起批

- **状态**: 已采纳
- **日期**: 2026-09-21
- **依据**: ADR-0042 决定 6e（逐项例外）；ADR-0052 决定 6（挂起批需新 ADR
  解冻）；`docs/architecture-hardening-plan-2026-09-19.md` §三、§四、§五
- **关系**: 解冻架构加固计划 §三的 R1/R2、R3、R7、配置 fail-fast、扩展点注册表
  与 R4 残余；不改探针线判据、自用线阈值，也不新增产品功能

## 背景：为什么现在解冻

ADR-0052 决定 6 把 §三挂起批的触发条件设为 ADR-0042 探针线到
2026-09-23 24:00 判定线后的强制评审，并要求解冻必须由新 ADR 或逐项引用
6e 完成。当前日期为 2026-09-21，判定线尚未到达，分发清单仍有四项未发出。

因此，本次解冻**不是探针时钟得出的结论**，也不代表探针线已经通过、失败或
改变口径。它是项目所有者基于当前开发节奏主动做出的范围决策：在不等待
09-23 评审的前提下，按既有施工单连续执行架构加固。

选择现在执行的三条依据：

1. §三已经把 R1/R2、R3、R7、配置 fail-fast、扩展点注册表与 R4 残余的目标、
   顺序、回滚粒度和验收命令写成可施工状态；继续等待不会产生新的设计信息。
2. ADR-0052 已把分层债务量化为 **9 条违规、56 个循环、332 处
   `api_module._` 引用站点**。R1 越晚执行，后续产品和探针相关改动越容易继续
   向组合根增加耦合。
3. 本批全部是内部结构、配置错误处理和错误归因收口，不改变用户可见产品能力；
   探针与自用线可以继续独立推进，不被本批阻塞。

## 决定

**决定 1（解冻范围）**：按 `docs/architecture-hardening-plan-2026-09-19.md`
§三既定顺序解冻全部挂起批：

1. §3.1 R1/R2：应用层承接编排，先消除服务层对 `resualign.api` 的反向依赖；
2. §3.2 R3：拆 `update_job` 与 `_run_job_holding_gate` 两个 god method；
3. §3.3 R7：领域目录分包；
4. §3.4 配置 fail-fast；
5. §3.5 扩展点注册表；
6. §3.6 R4 残余：删除错误 message 子串嗅探。

R7 必须在 R1 之后，避免目录移动与 R1 的大范围引用迁移产生不可审阅的 diff。

**决定 2（判据不动）**：ADR-0041 决定 4 的探针线数值、ADR-0040 需求线 (a)
口径和 ADR-0042 的双线、时钟、护栏一字不改。本 ADR 只解冻工程加固，不把
探针状态改成已评审，也不提前登记任何判定结果。

**决定 3（逐批纪律）**：§3.1 的每个 services 文件独立可回滚；R3、R7、配置
fail-fast、扩展点注册表、R4 残余分别按施工单粒度提交。每批必须满足：分层
棘轮不新增、全量后端测试绿、前端测试绿；涉及端到端启动或路由的批次补跑
Playwright/E2E。

**决定 4（棘轮收紧）**：R1/R2 完成后必须运行
`python -m resualign.tools.modgraph --update` 收紧基线。`api_module._` 代码
引用站点必须归零；测试通过时仍保留的历史测试替换点也应迁到新组合根，
不得把测试兼容当成目标架构。

**决定 5（不做）**：本 ADR 不放宽 CI 门禁，不改变 HTTP 错误体契约，不新增
用户功能，不把 R1 设计成第二套全局服务定位器。原施工单中明确留给后续阶段
的字体二进制、视觉样张入库等事项不在本批内。

## 后果

- §三从“等待 09-23 评审”转为物主授权的连续施工线；探针线仍可独立判定，
  两者结果不会互相顶替。
- R1 会先改变内部依赖方向和测试替换点，再进入函数拆分与目录迁移；任一服务
  文件迁移失败时停在该提交，不回滚已经完成且验证通过的部分。
- 架构加固完成后，领域、服务和组合根的边界由棘轮基线固定，下一轮产品改动
  不需要从这个批次的末尾重新证明授权。

## 与既有 ADR 的关系

- **ADR-0042**：冻结令由本 ADR 按“新 ADR 解冻”路径覆盖，仅限 §三范围；
  探针判据、自用线阈值和 6b/6c/6d 护栏不变。
- **ADR-0052**：本 ADR 取代其决定 6 中“必须等 09-23 判定线后评审”的时间门，
  其他现在批结论和棘轮机制保持有效。
