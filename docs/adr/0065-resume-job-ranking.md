# 0065 — 简历 × 岗位确定性排序（ranking-first）

- **状态**: 已采纳（提案当日 2026-10-26 定案）— 7 项未决事项的定案见「拍板记录」
- **日期**: 2026-10-26
- **关联**: ADR-0059（P0 自用线 / P1 feature flag）；ADR-0064（prematch 词面信号，
  本文对其「不做嵌入向量」一条作**限定性修订**）；ADR-0060 / 0061（allowlist 与
  `jd_context` 边界）；ADR-0041 决定 11（`gate.py` vendor 锁）；ADR-0055（导入
  去重前置，重复行 0 次 LLM）；#167（门禁逐条隔离）
- **上游**: 不涉及（零触碰 `gate.py` 与 `tests/fixtures/gate/`）
- **设计草案**: `docs/plans/resume-job-ranking-design-2026-10-26.md`
  （实现细节以草案为准；本 ADR 只记录决策与边界）

## 背景

**1. 规模事实**。`data/jobs.db` 只读实测（2026-10-26）：真实岗位 **333** 条
（另有 189 行标题为 `B` 的测试夹具，已排除）；`jd_text` 中位数 **2,793 字**、
最长 **9,028 字**；全库约 **90 万字**（粗算 60–90 万 token），
**远超任何单次上下文**。跨库「找岗位」在技术上必须依赖检索，这不是可选项。

**2. 现有选岗方式有天花板**。当前是手动浏览 + `Ctrl+K` 零 LLM 快速评估
（`local_fallback` + `match_scorer` 关键字覆盖分），没有「以简历为条件」的
排序。`prematch.py` 记录的 508 份真实 JD 离线分析中，**40.6% 的岗位命中
≤1 个词表技能**——同义表述（「高并发」vs「支撑 QPS」）无召回。

**3. 岗位与简历之间没有矩阵**。`master_resumes` 283 行（绝大多数为测试租户
夹具，真实租户 `local` 下为个位数），**414 个岗位绑定过工作台简历**，但
「这个岗位该用哪份底稿」完全靠手动。选错底稿 → 缺口全是真缺口 → 编辑器无据
可改，正对应 209 个 failed 中 **43 个「未产出任何可用改写」**。

**4. 近重复在浪费运行**。按 `(title, company)` 归并，真实岗位中有
**41 组近重复、多出 41 行**，其中 79 行跑过工作台对齐；保守估计约
**41 次对齐是重复劳动** ≈ 41 × 194s ≈ **2.2 小时墙钟** + 配额消耗。

**5. 漏斗定位**。实测：可用建议 22 → 采纳 3 → `applications` 2 条。断点在
**产出与采纳**，不在「发现」。故本 ADR 只承诺两件事：把「翻 333 行」变成
「看 10 行」；把「选哪份底稿」从猜变成有分数。**不承诺**提升可用率——唯一可能
影响产出率的是 best-resume，须由评测证实。

**6. 与 ADR-0064 的冲突**。ADR-0064（2026-10-24）明确「不做嵌入向量/向量库
（违背零依赖）」。本文要过，必须同时给出**新证据**（§决策 4 的预注册评测）与
**新边界**（确定性接口、默认关闭、不进门禁）。二者缺一，则维持 0064，评测结果
写成否决记录——那同样是可交付物。

**7. 定位**。`docs/STATUS.md` 已把项目定位为「单机可复现的求职工作台 /
面试作品」。能力线动机正当，但必须在 ADR 中标注清楚，不得冒充产品需求。

## 决策

**1. 能力边界：新增三项，全部确定性、默认关闭**

仅以下三个消费者，均不进入 `gate.py` / allowlist / 内容级校验 / 编辑器事实校验：

| 消费者 | 形态 | LLM |
| --- | --- | --- |
| 简历 → 岗位 | `GET /api/jobs/recommended` | 否 |
| 岗位 → 底稿简历 | `GET /api/jobs/{id}/best-resume` | 否 |
| 导入近重复提示 | 导入响应字段 `similar_existing_job_ids`（只提示不拦截） | 否 |

**2. 排序关键路径零 LLM**

打分固定为：**结构化硬过滤（SQL）→ 词面 + 语义双路召回 → RRF（k=60）融合
→ 按 `job_id` 稳定排序**。LLM 最多用于「把自然语言条件解析成筛选参数」与
「把 top-10 总结成一句话」（可选交互皮，不进默认路径），**永不参与打分**。
理由：排序必须可复现、可回归、可进 CI；自由文本输出无法算 hit@10。

**3. 数据模型（迁移 47）**

新增 `job_embeddings` 与 `resume_embeddings` 两表，主键
`tenant_id + (job|resume)_id + model`，存 `dim` 与 `text_sha256` 以支持增量
与重建；不持久化简历×岗位矩阵（真实简历个位数，实时点积 25–40ms 足够）。
建库走独立后台任务并暴露进度，首请求不得阻塞。

**4. 评测先行，预注册判据**

先落评测（作者手工标注 40–60 条 × 2 份真实简历，二值相关，问法固定为
「今天只投 10 个，我会投它吗」），指标 hit@10 / recall@10 / nDCG@10 +
时间序基线 + 延迟，判据**事后不得重谈**：

| 结果 | 处置 |
| --- | --- |
| hit@10 相对关键字基线 **≥ +10pp** 且 p95 < 300ms | 产品化（flag 默认关） |
| **+5 ～ +10pp** | 保留接口与评测，不铺 UI |
| **< +5pp** | 关线，0064 维持原样，写否决记录 |

best-resume 另有补充判据：top-1 推荐与人工事后判断一致率 ≥ 70% 才保留接口。

**5. 失败语义：非阻断降级，与门禁严格分离**

embedding 超时 / 索引缺失 / 维度不匹配 / 模型漂移 → 一律**回退关键字排序**，
返回 200 + `degraded:true`，不 5xx、不抛错、不阻断主流程。**门禁是 fail-closed，
排序是可以降级的**——两套语义不得混用，并须有测试锁住「排序模块不 import
`gate`」。

**6. 开关与排期**

`RESUALIGN_RESUME_RANKING=0` **默认关闭**（与 `RESUALIGN_PREMATCH` 同风格）。
评测脚本与只读接口不占 P0；产品面在 P0（3 份真实 JD 自用验证）过线后才允许灰度，
且先灰度单个入口。UI 不得插队导航改造（ADR-0059 §1）。

**7. 技术边界：零新依赖、零向量库**

只用 `httpx` + 标准库；纯 Python 余弦（预归一化、内存缓存）。规模阈值
**5k 条**：超过时另开 ADR 评估 ANN，不提前引库。不引入 numpy / FAISS /
Chroma / LangChain。离线与 CI 一律走确定性 `HashingEmbedder`。

**8. 隐私边界**

默认本地 Ollama；若用户配置的是远程节点，embedding 文本与该节点聊天的数据
同等对待（同一信任边界），在 ADR 与用户文档中写明。

**9. 对 ADR-0064 的限定性修订**

仅修订其「不做清单」中的嵌入向量一条（措辞见附录 A），0064 已落地的 prematch
实现、词表、消费者与其余两条「不做」一律不动。

**10. 用户语言**

用户可见文案不出现「向量 / 相似度 / RAG」；只说「匹配度分位」「有据技能」
「建议底稿」（与 ADR-0059 §5 的内部术语隐藏规则一致）。

## 后果

- **正面**：岗位库从「人翻列表」变成「以简历为查询的排序服务」；把 333 行浏览
  压缩到 10 行决策；近重复提示可回收约 2.2 小时/季度的重复对齐；补齐「语义检索
  + 检索评测」能力线，且评测与降级路径都可进 CI。
- **代价**：多两张表与一个后台建库任务；多一类需要维护的开关与降级路径；
  标注集需要人工 2 小时且 3 个月内冻结。
- **明确不变**：`match_score` / `gap_report` / 编辑器 prompt / allowlist /
  门禁语义全部不动；P0 优先级不变；不宣称提升可用率（除非 best-resume 评测达标）。
- **风险**：标注集小可能过拟合（缓解：分层抽样 + 时间序基线 + 冻结）；排序分被
  误读为概率（缓解：只给分位）。

## 备选方案（已否决）

| 方案 | 否决理由 |
| --- | --- |
| 问答式 RAG（对话检索岗位） | 输出形态错（要列表不是段落）、结构化筛选被降级、不可复现不可评测；降为可选皮 |

## 判据口径澄清（2026-10-26 实现期，非阈值重谈）

决策 4 的判据原文写作「hit@10 相对关键字基线 ≥ +10pp」。实现期的冒烟结果暴露了
该措辞的口径问题：在 50 条样本、正例 20–33 条的规模下，**任意排序方法只要有一个
正例进 top-10 就命中，hit@10 恒为 1.000**（time_order / keyword / hashing_vector /
rrf 四组全部 1.000），没有区分度。

因此判据的主指标先按 `recall@10` 执行（该口径随后被下一条再次修正，保留原文以留痕），
`hit@10` 降为辅助读数；**+10pp 的阈值不变**，nDCG@10 / MRR 一并报告。
这是「二值指标在 50 条样本上饱和」的口径澄清，不是放宽或收紧判据。
若未来样本量扩到 hit@10 可区分的规模，另开 ADR 再议。

**第二次口径修正（同日、标注前）**：`recall@10` 在正例很多的标注集上会被数学
封顶——上限 = `10 / P`。用「岗位族」做代理标注冒烟（简历 A 44 个正例）实测封顶
**22.7%**，此时「+10pp」**不可能达成**，判据会退化成永远不达标。故主指标再改为
**`precision@10`**（top-10 里「会投」的占比，天然 0–1、不封顶，也正是用户的实际
效用：这 10 个里我投几个），`recall@10` / `nDCG@10` / `MRR` 作为辅助一并报告。

两次修正都发生在**任何人工标注产生之前**（当前标注表 0/50），只改指标定义、
**阈值 +10pp 不变**，因此不构成事后调整判据；标注完成后若还要改口径，必须整批重标
并新开 ADR。

**延迟口径**：判据里的 p95 < 300ms 指**排序路径**（向量已就绪后的余弦 + 融合，
实测 3–10ms），不含首次 embedding。bge-m3 本机 CPU 实测 **645–741 ms/doc**
（50 条 32–37s），因此 B 档必须缓存向量（`job_embeddings` / `resume_embeddings`），
冷启动只返回 `degraded:true` 走后台建库，不得阻塞请求。

复现依据：`benchmarks/resume_ranking_benchmark.py --selftest`；家族代理标注冒烟见
本地 `.scratch/ranking-a1/results-ollama-proxy.json` 与 `sanity-report.md`
（`.scratch/` 不入库，属过程数据，不构成质量证据）。

## 标注协议修订（2026-10-27，政策标签，替代逐条人工）

**为什么改**：决策 4 原定「作者逐条标注 40–60 条 × 2 份简历」。实测人工标注表 0/50；
三个自动替代源逐项试过、均不可用：

| 自动标签源 | 实测 | 结论 |
| --- | --- | --- |
| `jd_text` 历史结论（值得投 / 建议不投） | 高精度抽取仅 **71 正 / 7 负**（329 条），50 样本内 **10 正 / 0 负** | 无负例，P@10 失效 |
| `workbench_resume_id`（当初选哪份底稿） | 225 个对齐岗位里 **216 个同一份简历** | 是默认值，不是选择 |
| `applications` / 采纳 | **2 / 3** 条 | 样本量不足 |

**新协议（作者 2026-10-27 口述政策）**：

> 只投 后端 / 算法 / 数据 / 测试开发；运营 / 销售 / 外包不投；实习也投。

标签由规则生成（`benchmarks/make_policy_labels.py`）：

- 正例：`job_function ∈ {后端, 算法, 数据, 测试}` 且标题/公司不含外包词；
- 负例：`job_function ∈ {产品, 运营, 前端, 运维, 架构, 其他}` 或含外包词；
- 未分类（无 `job_function`，96 条）**排除**，不猜；
- 标签与简历无关（A/B 共用），与关键词排序、向量排序均无共享信号。

**判定集**：全库 233 条为「full 集」（198 正 / 35 负，正例占 85%，P@10 会饱和）；
另取全部 35 个负例 + 35 个确定性抽样正例构成「balanced 集」（随机基线 P@10 = 50%）。
**判据在 balanced 集上判定**，full 集只做饱和性交叉检查。

判据口径相应从「投递意愿」变为「**政策一致性**」；**+10pp 阈值不变**，主指标仍为
`precision@10`。

**结果（2026-10-27，bge-m3 / 1024 维，本机 CPU）**：

| 集合 | 简历 | keyword P@10 | vector P@10 | Δ |
| --- | --- | --- | --- | --- |
| balanced（35+35） | A | 0.200 | 0.800 | **+60.0 pp** ✅ |
| balanced（35+35） | B | 0.400 | 0.900 | **+50.0 pp** ✅ |
| full（233） | A | 0.600 | 1.000 | +40.0 pp（饱和交叉检查） |
| full（233） | B | 1.000 | 1.000 | 0.0 pp（饱和） |

**必须随数字一起传播的局限**：

1. 政策标签是**族级规则**，测「排序是否符合政策」，不测「你想不想投」；
2. 关键词基线存在大量 0 分并列、按 `job_id` 断裂，其 P@10 偏低含 tie-break 成分；
3. 结论应读作「向量对岗位族的区分度显著强于技能词重叠」，**不得**读作
   「投递效率提升 N 倍」；
4. 真正的意愿判据仍缺人类锚点；补齐方式（`annotation.html` 键盘版 15 分钟，
   或人工抽检）不阻塞 B 档 flag 开发，但阻塞「宣称收益」。

**B 档处置**：判据按新口径达标 → 允许进入 B 档开发，但仍须遵守决策 6（默认关、
P0 后灰度、UI 上限一处），且用户可见文案不得出现「向量 / 相似度」。

实现期决定（均以评测或实测为依据）：

1. **默认只走向量一路**，RRF 融合保留为 `RESUALIGN_RANKING_FUSION=1`（默认关）：
   2026-10-27 政策评测里 RRF 在简历 A 上 0.400，低于纯向量 0.800——融合拖低，先关。
2. **词面共召回不每请求跑正则**：评测实测 233 条 keyword 排序 2.2 s；改为索引期写入
   `skills_json`，查询期集合交集（毫秒级），RRF 才具备可用性。
3. **失败一律降级**：`disabled` / `resume_missing` / `resume_text_missing` /
   `embedder_unavailable` / `embedder_failed` / `index_empty` / `job_text_missing`；
   HTTP 仍 200，与门禁的 fail-closed 分离。
4. **best-resume 只读**：不写 `workbench_resume_id`（决策 6）。
5. **建库为后台 daemon 线程**（每租户一个在飞），冷启动返回 degraded，不阻塞请求。

新环境变量：`RESUALIGN_RESUME_RANKING`（默认 0）、`RESUALIGN_EMBED_PROVIDER`
（auto/ollama/openai/hashing）、`RESUALIGN_EMBED_MODEL`、`RESUALIGN_EMBED_URL`、
`RESUALIGN_EMBED_API_KEY`、`RESUALIGN_EMBED_BATCH`、`RESUALIGN_EMBED_TIMEOUT`、
`RESUALIGN_RANKING_FUSION`。

验证：新增 43 个用例（engine 12 / storage 12 / service 14 / endpoints 2 / platform 2 等），
覆盖批量与超长切分、维度漂移、租户隔离、sha 增量、降级 reason、best-resume 不写回、
路由顺序（`/api/jobs/recommended` 必须先于 `/api/jobs/{job_id}`）与「排序模块不 import
`gate` / 聊天客户端」的静态断言。

## 附录 A：对 ADR-0064「不做清单」的修订措辞

原文：

> 明确不做：嵌入向量/向量库（违背零依赖）、技能图谱数据库（过度设计）、
> 全自动岗位排序（与「受控」定位冲突，见 ADR-0059）。

修订为：

> 原「明确不做嵌入向量」一条由 ADR-0065 限定性修订：prematch 仍为**零网络、
> 零依赖的确定性信号**，不引入 embedder；语义相似仅作为**简历×岗位排序**的
> 一路召回信号，接口**默认关闭、确定性、不进 `gate`/allowlist/编辑器提示**，
> 评测判据与不引向量库的规模阈值（5k 条）见 ADR-0065。其余两条不变。
