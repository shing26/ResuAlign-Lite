# ADR-0019: ResuAlign 2.0 architecture decisions

Status: accepted (2026-08-04)

## Context

ResuAlign 2.0 upgrades the 1.0 baseline from a resume rewriting tool into a
job application decision console. The cross-team design session produced
several decision points that need an explicit record before implementation.

## Decisions

1. Frontend stays buildless Vanilla ESM with CSS variables and optional Light
   DOM Web Components. No React/Vue/Tauri in 2.0; Tauri is evaluated as a P2
   spike only.
2. Structured JSON is the single source-of-truth contract between the LLM and
   the pipeline. SSE (or polling) only carries stage/result progress events;
   token-level streaming is out of scope for P0.
3. Zero hallucination is a hard gate. Rewrites may only rephrase, reorder, or
   re-emphasize facts already present in the source resume. Every diff carries
   provenance, and P0 adds provenance quotes plus source spans.
4. Granularity stays fine/medium/coarse with medium as the default; batch
   alignment defaults to fine; coarse is a deliberate user choice.
5. SQLite is unified on WAL, busy_timeout=5000, foreign_keys=ON and
   synchronous=NORMAL. Job transitions use durable claims so a restart can
   safely requeue interrupted work.
6. The pipeline board uses the job library status as its single source of
   truth; application records are treated as derived state.
7. Multi-tenant scope: 2.0 ships data/API isolation only; the UI remains in
   personal mode.

## Consequences

- Contract and golden tests guard the public API during the `api.py` split.
- LLM prompt versions are cache keys; cache hits must never serve a different
  prompt version or tenant.
- Frontend selectors and hash routes are part of the contract for the
  Playwright smoke suites.

## Post-review amendments (2026-08-04)

- Provenance hard gate is now enforced for the production `OpenAIClient`:
  `strict_provenance = True`; diffs whose quote cannot be found in the source
  resume are moved to `invalid_diffs` instead of being returned.
- Job claims are atomic: `_run_job` claims `queued -> running` and exits when
  another worker already claimed the job; restart recovery requeues running
  jobs before restarting workers.
- `ContentCache` uses the shared SQLite pragma set and is wired into
  diagnosis, JD analysis, classification, and engine runs through the API
  layer.
- HTTP middleware now assigns `X-Request-Id`, emits structured request logs,
  and logs slow calls above 3s.
- Batch alignment accepts either library `job_ids` or raw `jd_urls`, and runs
  evaluation per row so the comparison matrix includes an eval score.

## Deferred P1/P2 items (not blocking this delivery)

- Model tiering (`fast_model` / `reasoning_model`) is deferred to a later
  release; current config keeps one model.
- `ContentStore` exists with tests but is not yet wired into the job/resume
  stores; large-text externalization and backup migration remain P1.
- Web Components, Tauri spike, full-result cache, analytics, and dedicated
  granularity benchmarks remain P2 spikes per `docs/tickets-2.0.md` T9.
