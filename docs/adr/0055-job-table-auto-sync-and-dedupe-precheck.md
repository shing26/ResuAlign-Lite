# ADR-0055: 用户主动解冻 — 岗位表自动同步与导入去重前置

- **状态**: 已采纳
- **日期**: 2026-09-22
- **依据**: ADR-0042 决定 6e（逐项例外）；用户主动派单（岗位表每日增长，
  要求解决二次导入重复并增加自动获取）
- **关系**: 只解冻本 ADR 列出的范围；不改探针线判据、自用线阈值与
  ADR-0042 的 6b/6c/6d 护栏，不解除 ADR-0041 决定 1 的功能票冻结

## 背景：实测数据推翻了两条先验

用户每天在 WorkBuddy 侧追加同一张 `岗位总表.csv`，再手工导入 ResuAlign，
因此提出两个问题：**二次导入会不会重复**、**能不能自动获取**。

在真实实例上取证后得到两条与直觉相反的结论：

1. **去重已经在生效，重复的不是数据而是成本。** 用同一份 47 行的导入文件
   二次导入，结果是 `created=0 / skipped=47`，跳过原因全部是
   `Duplicate job already exists`，库里没有多出一行。但这次"什么都没做"的
   导入付了 **47 次 LLM 分类调用**（`data/logs/app.log` 12:24–12:32，约
   8.6 分钟、每次 attempts=2、每次约 3.5k 输入 token）。原因是
   `_create_job_from_source` 先调 `_classify_job` 再调 `create_job`，
   去重键在插入时才计算——重复行要买一次"被拒绝"的票。
2. **去重身份对"JD 正文被改写"不成立。** 没有可用投递 URL 的行，去重键是
   JD 正文的哈希（`text:sha256(...)`）。WorkBuddy 重写某条 JD 的 markdown
   正文时，同一岗位会得到新哈希，于是重新入一份。

## 决定

**决定 1（去重前置）**：`_create_job_from_source` 在调用分类器**之前**完成
去重判定，判据与 `create_job` 落库时写入的键完全同源
（`job_library._dedupe_key_for`：有可用 URL 用归一化 URL，否则用 JD 正文哈希）。
命中即抛出原有的 `Duplicate job already exists`，导入批次仍计入 `skipped`，
HTTP 单条建岗仍是 409。**重复行从此 0 次 LLM 调用。**

**决定 2（岗位表稳定身份）**：经岗位表同步进入、且没有可用投递 URL 的行，
去重键改用 `jobtable:sha256(company|title|location)`（大小写/空白归一）。
动机是决定 1 暴露的身份缺陷：JD 正文重写不应产生新岗位。有真实投递 URL 的
行仍以 URL 为准，因为那是更强的同一性信号。代价是同一公司+同标题+同地点的
两条真正不同的岗位会被视为重复——这是有意的取舍，改回正文哈希会把
"WorkBuddy 改写 JD"重新变成重复来源。

**决定 2a（升级兼容）**：同步在入队前先按新键过滤一次；对没有 URL 的行，
新键未命中时再查一次 JD 正文哈希，因此升级后第一次同步不会把既有
（ADR-0055 之前入库、键仍是正文哈希的）行整批重加一遍。残留缺口：
ADR-0055 之前入库的行若在第一次升级后同步前恰好被改写过正文，仍会多出一行，
此后该行带稳定键，不再重复。

**决定 3（岗位表配置落库）**：`user_settings` 迁移 11 新增 `job_table_json`，
存 `path` / `jd_dir` / `auto_sync` / `interval_minutes` / `preanalyze`，以及
服务端只写的 `last_sync_at` / `last_result`。`SettingsUpdateRequest` 新增
**加性**属性 `job_table`，部分更新语义与既有 `llm` 段一致（省略即不动，
显式 null 即清空）。`auto_sync=true` 而 `path` 为空时 422。

**决定 4（服务端读取 + 复用导入管线）**：新增
`GET /api/jobs/job-table`（读配置与上次结果）与
`POST /api/jobs/job-table/sync`（立刻同步一次）。同步读服务端路径上的 CSV，
按列别名兼容 WorkBuddy 原始表头（公司/岗位/薪资/地点/投递入口/JD文件）与
ResuAlign 自己的导出表头；表里只有 `JD文件` 引用时，从 `jd_dir` 内联正文。
行交给既有导入 worker，因此去重、预分析、跳过原因与手工导入是同一套契约。

**决定 5（后台自动同步）**：API lifespan 启动一个 60s tick 的守护线程
（与 #102 watchdog 同形，停止事件随 lifespan 关闭），按租户的
`interval_minutes` 判定到期后触发同步。关闭开关为环境变量
`RESUALIGN_JOB_TABLE_SYNC=0`。

**决定 6（服务端文件读取的安全边界）**：个人模式（单机桌面默认，本仓
`_PERSONAL_MODE`）信任本机用户；多租户部署必须设置
`RESUALIGN_JOB_TABLE_ROOT` 且路径解析后落在该目录内，否则 422。读取端固定
扩展名白名单（`.csv`/`.txt`）与 8 MB 上限，避免把"配置一个路径"变成任意
文件读取原语。

**决定 7（契约同步）**：新端点属加性变更，`contracts/openapi-current.json`
与 `contracts/incremental/manifest.json` 同步登记；
`contracts/openapi-v1.json` 不变。

**决定 8（不做）**：不改探针判据与时钟，不新增运行时依赖，不做网络抓取
（后台爬 JD 仍然下线），不改成本护栏的后端执行路径——此前删除的只是导航栏
与设置页的展示面板，`api/services/cost_guard.py` 的限流与日限额继续生效。

## 后果

- 二次导入从"8.6 分钟、47 次 LLM 调用"降到"0 次 LLM 调用"，且结果同样
  不新增行；反复同步是安全的。
- WorkBuddy 改写已入库岗位的 JD 正文不再产生重复行。
- 岗位表从"手工挑选文件导入"变成"配置一次、按间隔自动补新行"，仓库里的
  岗位表不再是每次都要人工搬运的中间产物。
- 代价：同步是**服务端**读文件，因此配置里是服务器可见路径；远程/容器部署
  需要把路径挂载进去（多租户另有 root 白名单约束）。
- 代价：决定 2 的稳定身份在极端情况下会把"同公司+同标题+同地点"的两条不同
  岗位判为重复，需要人工用 URL 区分。

## 与既有 ADR 的关系

- **ADR-0042 决定 6e**：本 ADR 即该条的逐项例外记录（用户主动派单、
  "让自用闭环好用"），冻结令其余部分继续有效。
- **ADR-0053**：其范围是架构加固 §三，不含产品功能面；本 ADR 只覆盖岗位表
  同步与导入去重，两者不互相授权。
- **ADR-0041 决定 1**：功能票总闸（#114 `frozen`）不变，本例外不外溢。
