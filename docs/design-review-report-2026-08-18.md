## 一、UI Finish-Gate Reviewer — 设计守门评审

### 产品透镜

| 维度 | 当前状态 |
|------|----------|
| 用户 + 任务 | 自托管求职者，在个人电脑上完成岗位分析→简历定制→投递跟进闭环 |
| 首读对象 | 岗位库的待办状态或仪表盘的 KPI 数字 |
| 核心动作 | 选择一个岗位、查看对齐结果、记录投递、安排跟进 |
| 密度决策 | 紧凑（13px 字号，rail 侧边栏，数据优先） |
| 交互模型 | 左侧导航 + 右侧视图切换，工作台为 split 双栏 |
| 响应式优先级 | 侧边栏折叠 → 视图内堆叠 |

### 发现的问题

#### P1: 仪表盘（Dashboard）是通用 KPI 面板，没有产品特异性

**实际现象**：`dashboard-view.js` 渲染的数字卡片（简历数、岗位数、投递数、面试数、Offer 数、放弃数）是标准 KPI 条，没有"下一步该做什么"的引导。

**产品证据**：一个求职工具的核心不是"看数字"，而是"知道此刻该做什么"。当前仪表盘回答的是"过去发生了什么"，不是"现在该干什么"。

**门禁要求**：首页必须展示排好优先级的待办事项，KPI 数字退为辅助信息。

#### P2: 工作台缺少持久化进度指示

**实际现象**：`workspace` 的 session 有 30 分钟 TTL，但用户没有"当前处于哪个阶段"的可见指示。

**产品证据**：对齐过程有 5 个阶段（diagnose → profile → gap → tailor → evaluate），但 UI 只在 SSE 事件中推送，用户看不到"已完成 3/5 阶段"的进度。

#### P3: 今日待办（Today View）是纯列表，缺少时间紧迫性和优先级

**实际现象**：`todayViewHtml` 生成列表，但所有 item 等宽，没有视觉区分"今天必须处理"和"可以稍后"。

#### P4: 空状态通用

**实际现象**：当岗位库为空时，显示空列表而非引导性内容。首次使用用户不知道"我应该先做什么"。

### 通过门禁条件

- [HOLD] 仪表盘需要改为"待办优先"视图
- [HOLD] 工作台需要可见的阶段进度条
- [HOLD] 今日待办需要优先级视觉区分
- [HOLD] 空状态需要引导

## 二、Persona Walkthrough Specialist — 角色模拟走查

### 角色档案

```
姓名: 张明 (26M)
身份: 计算机硕士应届生，正在投递后端开发岗位
技术背景: 熟悉 Python/Go，用过 Ollama，对自托管工具有好感
设备: 14 寸笔记本，1920x1080 
到达路径: 从 GitHub 发现此项目，按 README 启动
当前状态: 刚毕业，投了 20 家没消息，焦虑中
决策风格: 重度研究者，会读完整文档
依恋倾向: 焦虑型（需要每一步都有正反馈）
```

### 走查记录

**第 1 屏 — 仪表盘（首次进入）**

> 内心独白："嗯，RA 图标，ResuAlign Career Studio。三个简历，11 个岗位… 但我的简历在哪里？我该怎么开始？"
>
> 分析：用户看到 KPI 数字但不知道下一步。仪表盘没有引导"导入你的第一份简历"或"抓取你的第一个 JD"。

**第 2 屏 — 岗位库（点击后）**

> 内心独白："哦，这里是我之前粘贴的 JD。有个分类标签，但匹配分是空的。我需要对谁做对齐？"
>
> 分析：岗位库展示列表但没有"推荐优先级"排序。用户面对 11 个岗位不知道先处理哪个。

**第 3 屏 — 工作台（选择一个岗位后）**

> 内心独白："好，现在我看到了 JD 分析和我的简历。点击对齐… 它在转了。转了多久？30 秒了，我不知道它有没有卡住。"
>
> 分析：对齐过程没有进度百分比，用户不知道剩下多久。焦虑型用户会在这时刷新页面。

**第 4 屏 — 对齐结果（等待后）**

> 内心独白："匹配度 82%，差距分析说缺 Redis 关键词。然后我该做什么？我看到 diff 了，但怎么采纳？"
>
> 分析：diff 采纳的交互是按钮式，但用户预期是"一键应用所有建议"的流程。

**第 5 屏 — 投递后**

> 内心独白："好，我投了这家。然后呢？系统没有告诉我下一步该做什么。我自己去记日程吗？"
>
> 分析：投递后没有自动设置跟进提醒，用户需要手动"安排跟进"。焦虑型用户需要"3 天后提醒你跟进"的自动行为。

### 关键发现：设计师假设 vs 用户实际想法

| 设计师假设 | 用户实际想法 |
|-----------|------------|
| "用户想看 KPI 数据" | "用户想知道下一步做什么" |
| "用户会主动探索所有功能" | "用户只想知道如何完成当前任务" |
| "用户理解我们的术语" | "用户对'对齐''画像''差距'等术语感到迷惑" |
| "用户会等 LLM 完成" | "用户需要知道还有多久" |
| "用户会记住所有状态" | "用户需要系统提醒" |

## 三、Whimsy Injector — 趣味注入建议

### 品牌个性策略

```
专业基调: 自信、精准、可靠（求职工具需要信任感）
轻松时刻: 完成对齐、采纳 diff、记录投递时
错误时刻: 幽默但不轻浮，"LLM 在思考"、网络错误
成功时刻: 庆祝拿到 Offer，但保持克制，毕竟这是求职
```

### 微交互注入

#### 1. 对齐进度 — 打字机效果

当 LLM 在生成结果时，不是用 spinner，而是用渐显的"打字机"效果展示阶段名称，同时显示一个小动画：

```
JD 分析中 ████████░░ 80%
差距分析   ██████░░░░ 60%
简历改写   ████░░░░░░ 40%
```

每个阶段完成时微震动（CSS keyframe pulse）。

#### 2. 采纳 diff 的"盖章"反馈

当用户点击"采纳"时，diff 卡片有一个 0.3s 的"盖章"动画（绿色印章从左上角压入，带轻微缩放和阴影），然后卡片淡出。

#### 3. 空状态动物

当前空状态是空白页面。改为一个 SVG 小浣熊或柴犬，配文：

- 岗位库为空："还没有岗位，去粘贴一个 JD 吧！🦝"
- 简历为空："写一份简历，让工作来找你 🐕"
- 今日待办为空："今天没有待办，休息一下或者逛逛新岗位 🐱"

#### 4. 完成仪式

当用户标记"已拿 Offer"时，触发一个 2 秒的微庆祝动画：

- 顶部出现彩带渐隐效果（纯 CSS）
- 显示："🎉 恭喜！你从 {n} 份简历中脱颖而出"
- 自动生成"求职报告"PDF 的按钮

### 彩蛋建议

- **Ctrl+K 命令面板**：输入 `konami code` 触发隐藏模式（打字机速度变快/变慢）
- **深夜模式**：在凌晨 2-5 点打开时，问候语变为"这么晚还在找工作？辛苦了 🌙"
- **简历版本号**：当版本号达到 v10 时，显示"十项全能！你改过 10 次简历了 💪"

## 四、UX Researcher — 用户体验研究验证

### 当前行为分析

基于当前 API 数据（3 份简历，11 个岗位，0 个投递记录），可以推断：

**用户行为模式**：
- 用户导入了简历和岗位，但**没有完成投递闭环**
- 可能的原因：不知道如何操作、对齐过程太慢、对结果不满意

**关键研究问题**：
1. 用户从导入 JD 到记录投递的转化率是多少？（当前为 0%）
2. 用户在哪一步放弃了？是对齐阶段？还是看到 diff 后？
3. 用户是否理解"采纳 diff"的交互？还是期望全自动改写？

### 假设验证

| 假设 | 验证方法 | 预期结果 |
|------|---------|---------|
| 用户需要更多引导 | 5 用户可用性测试 | 首次使用需要≤3 步完成一次对齐 |
| 对齐时间影响留存 | 测量 LLM 调用耗时与放弃率的关系 | >30 秒时放弃率显著上升 |
| 用户期望自动跟进 | A/B 测试自动 vs 手动跟进提醒 | 自动提醒跟进率提高 2x |

### 推荐的数据采集

1. 前端埋点：`onboarding_stage`（用户当前处于哪个阶段）
2. 漏斗追踪：`jd_imported → aligned → diff_accepted → applied → followed_up`
3. 时间追踪：每个阶段的耗时（LLM 调用 + 用户决策时间）

## 五、UI Designer — 视觉设计系统评审

### 现有设计系统分析

| 维度 | 当前状态 | 评价 |
|------|---------|------|
| 颜色 | 深色主题，绿色 dot 表示状态，`#bg-appbg` 背景 | 功能性强，但缺少品牌色 |
| 排版 | 13px 基础字号，`text-[13px]`，rail 用 `text-xs` | 紧凑型，适合数据密集场景 |
| 间距 | Tailwind 风格 class，`space-x-3` 等 | 一致但偏紧 |
| 组件 | 按钮（btn btn-primary/ghost）、输入框（input）、badge、pill | 基础组件完整，但缺少设计 Token |
| 响应式 | `app-shell` flex 布局，rail 固定宽度 | 侧边栏在窄屏下会折叠 |

### 改进建议

#### 1. 建立设计 Token

当前 CSS 以 utility class 为主（`text-white/90`, `bg-appbg`），缺少可在单个文件中统一管理的关键 Token：

```css
:root {
  --color-brand: #4f8cff;         /* 品牌蓝 - 用于主操作按钮 */
  --color-brand-hover: #3a7ae8;
  --color-bg-app: #0f1117;        /* 背景色（当前硬编码） */
  --color-bg-card: #1a1d27;       /* 卡片背景 */
  --color-text-primary: rgba(255,255,255,0.9);
  --color-text-secondary: rgba(255,255,255,0.6);
  --color-accent-green: #22c55e;  /* 成功状态，现有 dot-success */
  --color-accent-amber: #f59e0b;  /* 警告状态 */
  --color-accent-red: #ef4444;    /* 错误状态 */
  --font-size-xs: 11px;
  --font-size-sm: 13px;           /* 当前基础字号 */
  --font-size-base: 14px;
  --radius-sm: 4px;
  --radius-md: 6px;
  --radius-lg: 8px;
  --space-unit: 4px;
}
```

#### 2. 信息密度与层级

当前所有视图的密度是均匀的。建议：

- **仪表盘**：待办事项用大号卡片（16px 标题），KPI 数字用小号辅助行（12px）
- **岗位库**：每行展示岗位名 + 公司 + 匹配分 + 状态，紧凑但可扫描
- **工作台**：双栏布局，左栏 JD 分析（14px），右栏简历改写（13px），diff 卡片用 12px

#### 3. 暗色模式的一致性

当前已有 `dark` class 在 html 上，但 light 模式可能未完整实现。确保：
- 所有 `bg-*` 和 `text-*` 有对应的 light 模式值
- `theme-toggle` 按钮切换时，所有颜色平滑过渡

#### 4. 交互反馈

- 按钮 hover 状态：`brightness(1.1)` 或 `opacity: 0.9`
- 卡片 hover 状态：`border-color` 变亮 20%
- 选中状态：active tab 用品牌色下划线或背景色
