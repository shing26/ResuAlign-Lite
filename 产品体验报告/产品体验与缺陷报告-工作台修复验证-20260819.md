## 1. 体验总览 (Executive Summary)

* **体验角色**：新手画像（冷启动直觉路径） + 核心玩家（重复使用、跨视图验证、导出/另存/跟进闭环） + 破坏性测试者（API 直发、并发 PATCH、极端输入）
* **健康指数**：🔴 阻断级 —— 核心对齐主路径在默认配置下 6/7 失败率；跟进数据可被静默丢弃；ATS 健康度跨页面失真
* **核心体感**：产品骨架（岗位库、简历管理、工作台 UI、设置、移动端适配）成熟度高，但**三条关键链路仍不可信**：① 对齐默认参数几乎必失败且报错文案误导；② 跟进保存"假成功"（toast 成功但后端吞字段）；③ ATS 分数已持久化却到处显示"未诊断"。LLM 侧本轮受账户 402 欠费影响（约 17:38 起），润色/分类等 LLM 依赖功能无法完成正路径验证，已标注。

### 🔴 [Bug-01] 工作台对齐引擎 默认参数下核心对齐稳定失败，错误文案误导用户

* **严重级别**：P0-阻断
* **问题类别**：功能缺陷（LLM 输出契约 + 错误处理）
* **复现环境**：Chromium 1440×900 / 隔离实例 8765 / 对齐接口（UI 与 API 双通道复现）

#### 🐾 严格复现步骤 (Step-by-Step Reproduction)
1. 访问 `http://127.0.0.1:8765/#/workspace/<job_id>`（使用后端岗位 `5a668d6d2b5b4de6a4c1d84aefd058a1` 与主简历 `1a6f57e23f49424a8ac20ff3c435e307`）。
2. 保持默认对齐参数（coarseness=medium / focus=balanced），点击「运行对齐」。
3. 等待 17–22 秒后接口返回失败。
4. 观察页面错误提示与浏览器 Network 面板。

#### ⚖️ 现象比对 (Expected vs. Actual)
* **实际现象 (Actual)**：默认参数**连续失败 6/7 次**（t03_repro 3 连败 + 矩阵 4 变体中 3 败 + 首轮 1 败；仅变体 B: coarse/skills 成功 1 次）。接口返回 `LLMResponseError`，UI 文案为「**模型返回了空内容或无法解析的 JSON**」——与实际根因（schema 校验失败）完全不符，用户会误以为模型质量差或误删内容。
* **预期行为 (Expected)**：默认参数下稳定返回改写建议列表（10± 条 diffs 卡片）；失败时应带可读的「模型输出结构不符合预期」与可重试入口。

#### 🔍 疑似根因与线索 (Suspected Cause & Code Context)
* **疑似文件/位置**：
  - `src/resualign/api/schemas.py / schema_registry.py:71-74`：`TailoredResume.sections: dict[str, str]` 要求 sections 每项为字符串；
  - `src/resualign/llm/llm.py:380-416` `_chat_structured_json_mode`：pydantic ValidationError 时**同 prompt 盲重试 2 次**，无纠错重试；
  - `src/resualign/engine/engine.py:25` `TAILOR_MAX_RETRIES=1`；
  - `src/resualign/api/services/jobs.py:30-60` `_job_failure_detail`：schema 校验失败被映射成「空内容或无法解析 JSON」误导文案。
* **状态/网络线索**：服务端 traceback 确认 DeepSeek 对该主简历的 `sections.工作经历` / `sections.项目经历` 返回**嵌套 dict**（如 `{'某某电商 高级后...延迟性能指标。'}`），pydantic 校验失败；变体 B（coarse/skills）成功说明模型有能力输出合规结构，是**契约校验对模型输出的常见差异**。

#### 🤖 编码 Agent 专用修复 Prompt (Coder Agent Instruction)
> 修复工作台对齐链路在默认参数下稳定失败的问题。
> 1. 在 `schema_registry.py` 的 `TailoredResume` 校验前增加**容错归一化**：若 `sections` 某项为 dict/list，将其中文本字段 `json.dumps`（ensure_ascii=False）为字符串后继续校验；或将 sections 契约放宽并归一化输出。
> 2. 在 `llm.py::_chat_structured_json_mode` 中，捕获 pydantic ValidationError 后**携带错误摘要做一次纠错重派**（prompt 增加「上次输出中 X 字段不合法，原因：…」），而非盲重试。
> 3. 修改 `api/services/jobs.py::_job_failure_detail`：区分「模型返回空内容」「JSON 解析失败」「结构校验失败」三类，分别给出准确文案（如「模型输出结构不符合预期，正在重试」）。
> 4. 验收标准：默认 medium/balanced 参数对主简历+后端岗位连续 3 次成功返回 diffs；错误文案不再出现「空内容或无法解析的 JSON」误报；服务端日志不出现无信息盲重试。

### 🔴 [Bug-02] 跟进流程 跟进弹窗不改状态时保存“假成功”，timeline 字段被静默丢弃

* **严重级别**：P1-严重
* **问题类别**：状态同步（数据静默丢失）
* **复现环境**：Chromium 1440×900 / 隔离实例 8765 / 岗位库详情与 API

#### 🐾 严格复现步骤 (Step-by-Step Reproduction)
1. 打开已投递岗位（status=applied，如 `5a668d6d2b5b4de6a4c1d84aefd058a1`）的跟进弹窗（`open-job-followup`）。
2. **不修改状态下拉**（保持 applied），仅填写「下一步」内容（如 `API直发：约二面v2`）并保存。
3. 页面 toast 提示「跟进已安排」（成功）。
4. 刷新页面并查看岗位详情 / 时间线 → 岗位字段无任何变化，next_step、due、timeline 全部丢失。

#### ⚖️ 现象比对 (Expected vs. Actual)
* **实际现象 (Actual)**：前端 toast 显示成功（main.js:2665 `saveFollowup` 无条件成功提示）；而后端 `update_job`（job_library/__init__.py:1361-1387）命中 `append_only_snapshot` 分支（status=applied 且 current≠draft），**所有 timeline 字段（applied_at / next_step / next_step_due_at / interview_stage 等）被置 None 忽略**，仅追加一条不可变快照。API 直发 PATCH1（status=applied + next_step）同样不生效；仅当同时把 status 改为 interview（PATCH2）才生效。t04c 实测 toast「跟进已安排×」出现但 job 无变化。
* **预期行为 (Expected)**：保存跟进至少持久化 next_step 与 next_step_due_at；若产品语义要求必须同时变更状态，则 UI 应禁用保存或明确提示，后端不应静默吞字段还返回成功。

#### 🔍 疑似根因与线索 (Suspected Cause & Code Context)
* **疑似文件/位置**：
  - `api/routers/jobs.py:41-67` `_with_auto_followup`、`:357-372` PATCH handler；
  - `api/services/workbench.py:103-109` `_read_timeline_extras`（`_TIMELINE_FIELDS` 见 `api/state.py:93`）；
  - `src/resualign/job_library/__init__.py:1361-1387` append_only_snapshot 分支：`status=applied 且 current≠draft` → timeline 字段全忽略；
  - 前端 `main.js:2600-2680` job-followup handler、`:2665` saveFollowup 无条件成功 toast。
* **状态/网络线索**：t04d 两次 PATCH（PATCH1 不生效 / PATCH2 生效）为 API 级铁证；快照机制本用于保留已投递定稿，但被无条件套用到所有 applied 更新上。

#### 🤖 编码 Agent 专用修复 Prompt (Coder Agent Instruction)
> 修复跟进保存被静默丢弃的问题。
> 1. 在 `job_library/__init__.py::update_job` 的 append-only 分支前增加判定：若 PATCH 载荷**显式携带任一天 time_line 字段**（next_step / next_step_due_at / applied_at / interview_stage 等），则走常规更新而不是 append_only_snapshot；或为 append-only 增加「显式更新字段」白名单。
> 2. 后端在字段被忽略时返回 400/422 并说明原因，禁止 200 + 吞字段。
> 3. 前端 `saveFollowup` 改为按请求结果决定 toast；若后端返回错误则展示「保存失败：…」。
> 4. 验收标准：① 岗位为 applied 时在跟进弹窗填 next_step 保存 → 刷新后 next_step/next_step_due_at 可见；② 不改状态也不填任何 timeline 字段时，仍允许追加备注快照；③ 有道失败时用户可见明确错误提示。
