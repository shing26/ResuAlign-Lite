## 2. 按严重度分类的问题清单

### 🔴 阻塞级（P0）

#### P0-1 对齐主路径在实况中失败，且失败文案给用户错误归因（核心闭环不可达）
- **维度**：交互逻辑（错误处理/反馈）
- **现状**：实况点击「开始对齐」→ 排队 toast → 约 166s 后失败，横幅：「对齐分析在『JD 画像与差距分析』阶段失败：**模型响应超时，请检查 API Key 与网络连接后重试**」（实测 `GET /api/jobs/{id}/analysis-status` → `status=failed, stage=jd_analysis, elapsed=166.2`；截图 `shots/wb_align_failed_live.png`）。但 `/api/settings/status` 显示 Key 有效、连通性 2437ms——归因「检查 API Key 与网络」是误导；真实原因是该模型响应超过 Timeout 护栏（设置显示 40s/次）。
- **为什么不合理（Persona 视角）**：林然第 1 次失败会照做（检查 Key/网络），再去点一次、再烧 2 分钟、再失败，品牌信任在第 3 次失败时耗尽。错误文案对「是什么错、该怎么办」没有区分能力（Round2/4 已就该问题提过「按失败类别分类文案」，当前仍是一句笼统话）。
- **建议**：① 超时类失败文案改为「模型响应超时（本次耗时 Xs），可尝试：更换为更快的模型 / 暂时减少 JD 长度后重试」，不再归因 Key/网络；② 失败详情展示本次各阶段耗时与重试次数（Fogg:Ability，让用户看到「慢」，而不是「坏」）；③ 提供「换用备用节点重试」一键（设置里已有备用节点，前端没接）；④ 对同一任务的连续失败做节流/提示，避免无谓烧额度。
- **证据**：API 实测 + `split-canvas.js:1283-1297`（error 直透后端文案）+ `api/services/jobs.py` 失败映射。

#### P0-2 工作台失败态同屏出现 3 个对齐入口、2 套标签，且空态引导文案与真实 UI 全面对不上
- **维度**：交互逻辑（可发现性/一致性）
- **现状**（实况 DOM，失败态下同时存在）：
  - 顶栏按钮「重新运行对齐」（`btn-danger`，y=144）；
  - 红横幅内「重新运行对齐」（y=213）；
  - 画布空态卡“还没有对齐结果”内「开始对齐」（y=563）。
  - 空态步骤文案：「在**左侧**「优化设置」选择主简历 / 点击**右侧顶部**「开始优化」」——实际「优化设置」tab 在右栏 x≈1143（不在左侧），主按钮标签是「开始对齐」且位于画布中部，**三处描述与界面三处不符**（移动端同样复现，`mb_workspace` 的 `.resume-empty__steps`）。
- **为什么不合理**：失败态下不应再渲染“还没有对齐结果”的首次引导；同动作 3 入口 2 标签（开始对齐 vs 重新运行对齐）让用户怀疑自己看错页；引导文案与真实控件对不上时，焦虑型用户会认为产品不可信（LIFT:Clarity↓、Anxiety↑）。
- **建议**：① 失败/过期态：隐藏空态引导卡，只保留 1 个主按钮（顶栏 danger「重新运行对齐」），横幅内不再放第二个按钮；② 空态文案改为与当前 UI 一致：「在右上「优化设置」中选择主简历 → 点击下方「开始对齐」」；③ 把「开始对齐/开始优化」全站统一为一个动词（建议统一「开始对齐」）。
- **证据**：`shots/wb_align_failed_live.png`、`dom/workspace_job2.json`、`dom/mb_workspace.json`、`split-canvas.js:194-198` + `format.js:2126-2134` 文案。

### 🟠 高级（P1）

#### P1-1 简历档案页「隐藏」的内联编辑表单默认可见：整份 Markdown 在预览下方重复出现
- **维度**：UI（状态表达/反馈）
- **现状**：`#/resume/{id}` 页面加载后，`.resume-inline-edit` 表单（16 行 textarea，**内含整份简历源码 2433 字符** + 「取消/保存新版本」按钮）以 `display:flex` 直接渲染在预览文档下方（y≈2447，页面总长 >2800px）。根因：`styles.css:7998 .hidden {display:none}` 被**其后的** `styles.css:9560-9568 .resume-inline-edit {display:flex}` 覆盖。DOM 实测 `computed display: flex`、`textareaLen=2433`、按钮 取消/保存新版本 可见。
- **为什么不合理**：林然打开简历页，看到渲染好的简历下面又叠着一个巨大的源码编辑框，第一反应是「页面坏了 / 内容重复了 / 我是不是误触了编辑」；对「丢数据焦虑型」用户这是信任崩塌点。且「保存新版本」按钮离他可能看到的视口极远，误点即误存。
- **建议**：① 删除 `.resume-editor/.resume-inline-edit` 中的 `display:flex`（或给隐藏态加 `!important`/改用 `[hidden]` 属性驱动）；② 加回归测试「简历页初始无 textarea 可见」；③ 顺带修复编辑态时「返回当前版本」与「取消」的可见性回归。
- **证据**：DOM 探针（probe 输出）+ `styles.css:6308-6334/7998/9560-9583`。

#### P1-2 设置词表 → 岗位库联动断裂：同一页面两种状态数据源（自定义词表在卡片上不存在）
- **维度**：模块联动
- **现状**：岗位库**筛选栏与编辑弹窗**从设置词表渲染（`events.js:169-187` `vocabularyList` → `kanban.js:119-121`、`format.js:2574-2579`）；但**每张卡片底部的状态下拉**从内置常量硬编码（`format.js:985-987` `JOB_STATUS_CANONICAL/JOB_STATUS_LABELS`）。默认 5 状态恰与词表默认一致，所以只有用户自定义后才暴露分裂。
- **为什么不合理**：老周在设置里把「放弃」改成「婉拒」或加一个「待定」，回到岗位库：筛选里选得到，但卡片下拉里没有；他觉得「设置没生效」或者「系统出了两个状态体系」。同一语义字段两套源，是模块各自为政的典型（LIFT:Clarity↓）。
- **建议**：① 卡片下拉改走 `vocabularyList("statuses")`（与筛选共用一次请求，符合 Story-6「一次性获取」）；② 若状态含 lifecycle 硬语义（投递→面试→Offer），则设置页状态词表应当只允许改名不允许增删，并在设置页注明约束；③ 验收：自定义状态词后刷新岗位库，卡片下拉与筛选完全一致。
- **证据**：`format.js:983-1017` vs `kanban.js:95-121`；实况 `dom/jobs2.json`（卡片 select 5 项与筛选 select 5 项同源但代码路径不同）。

#### P1-3 驾驶舱「快速继续」把失败/过期的任务当「待完成」推荐，进入即失败横幅
- **维度**：模块联动（驾驶舱 ↔ 工作台）
- **现状**：实况 `quick_continue` 推荐的任务在我执行对齐失败后仍被推荐（标题旁标「待分析/继续对齐」，无失败标识）；dashboard KPI「已完成对齐 6/11」统计 `alignment_status=="succeeded"`，但快速继续卡片不消费失败状态——失败任务与从未运行的任务在驾驶舱无法区分。
- **为什么不合理**：林然在驾驶舱看到「继续对齐」，点进去是红色失败横幅 + 已花掉的 2 分钟。驾驶舱的职责是其决策台，推荐一个已知失败的任务等于把错误信息做成快捷入口（LIFT:Anxiety↑）。
- **建议**：① `quick_continue` 对 `failed/canceled/expired` 任务标「上次失败 · 重新运行」并在卡片用警示色；② 若无 pending 任务，推荐策略改为「最近 24h 有进展」的任务而非「最新 updated_at」；③ 点「继续对齐」前无任务可做时直达岗位选择器。
- **证据**：`dom/dashboard.json`（continued card 文案「待分析」+ pill-warn）+ `api/routers/dashboard.py` 的 quick_continue 选择逻辑 + 实测失败后 dashboard 仍推荐同一 job。

#### P1-4 移动端工作台可达性差：主要操作与 tabs 在视口外 ~700-1500px
- **维度**：UI（移动端适配）
- **现状**（390×844 实测）：工作台顶部信息区占 134→~600px；「去投递/记录投递/重新运行对齐」在 y≈640；空态卡 y≈1007-1215；关键 tabs「岗位分析/面试记录/优化设置」在 **y≈1550**；失败横幅残留一个 9×18px 的「×」（y=804）。用户要在 390 宽屏里滚过 ~1500px 才能碰到流程 tabs。
- **为什么不合理**：阿泽在手机上打开工作台，只看到顶部信息 + 一屏空态，不知道下面还有操作；tabs 到 1550px 意味着「分析/设置」几乎不可达；9px 的 × 是不可点的（触控目标 <44px 硬伤）。
- **建议**：① 390px 断点下将各面板改为可折叠手风琴，把「岗位分析/面试记录/优化设置」tabs 固定在视口内（sticky 或顶栏 tab）；② 主按钮「开始对齐」上移或 sticky；③ 关闭横幅按钮 ≥32px 且带 aria-label。
- **证据**：`dom/mb_workspace.json`（buttons y 坐标、resume-empty box、× 9×18px）。

#### P1-5 技能缺口面板出现整句 JD 要求作为「技能」：抽取层把长句当技能
- **维度**：UI/数据模型（信息噪音）
- **现状**：驾驶舱「技能缺口」第 7 项为「AI Agent 基本概念（LLM API 调用、工具调用/Function Calling、MCP 协议等）或对 AI+运维方向有浓厚兴趣」——这是 JD 的一句 requirement，被当作技能计数 1 岗；桌面渲染为 90px 高、324px 宽的卡片，移动端 119px 高的横幅（桌面 x=1053 y=642；移动 y=1797）。根因：`skill_gaps` 来源于 JD must_have 长句未做短语化。
- **为什么不合理**：林然扫技能缺口想快速知道「市场要什么技能」，看到一句招聘文案会觉得这是公告栏不是分析面板；长句 chip 破坏视觉节奏，真正的高频短技能（Python/Java/Go）反而被稀释。
- **建议**：① 抽取层对 must_have 做短语化（按顿号/逗号/括号切分 + 长度阈值，>12 字或含「或」「等」的句子不进技能缺口）；② 前端对超长文本截断 + title 全名，禁止把句子渲染成整块（LIFT:Distraction↓）。
- **证据**：`dom/dashboard.json`（skill 项原文与 box h=90）、`dom/mb_dashboard.json`（h=119）、`api/routers/dashboard.py` skill_gaps 组装。

#### P1-6 对齐失败文案/状态与「今日待办-待跟进 0」等跨模块口径仍需回归
- **维度**：模块联动
- **现状**：顶栏「待跟进」hint 仍是「48h 内到期口径」（`dashboard-view.js:109`），后端实现为 `due >= today`（`api/routers/dashboard.py`，含未来所有）——文案与实现口径不一致（此问题在 Round2 报告过，未改）。历史 Bug-08 场景（驾驶舱 1 条/今日待办 0 条）的代码修复已落地，但文案侧漂移仍在。
- **为什么不合理**：老周若某天驾驶舱出现数字，会拿 hint 对质：「说好 48h，怎么 3 天后的也算？」跨模块口径不一致是信任杀手。
- **建议**：统一为「未过期待跟进」；或后端收紧为 48h。低工作量。
- **证据**：源码两处 + Round2 报告引用。

#### P1-7 简历「去对齐」深链断链风险：无目标岗位时落到岗位选择器且无简历上下文
- **维度**：模块联动（简历中心 → 工作台）
- **现状**：简历诊断卡「去对齐」`data-action="diagnosis-to-align"` → `#/workspace?resume={id}`（或带 job）→ 工作台岗位选择器不显示当前简历，选中岗位后也不会自动带入选中的简历，用户需在「优化设置」里再选一次简历。
- **为什么不合理**：林然从诊断结论直接去改简历的对齐版本，期望「简历和这个岗位对上」，结果选岗位后还得手动重申「用哪份简历」——意图链断开一次，忘记选简历还会用错基线。
- **建议**：① 工作台岗位选择器显示「已带入简历：xxx」，选中岗位后自动绑定该简历（写回 `workbench_resume_id`，岗位卡已存该字段）；② 无 job 时选择器上方给一行「你从简历 xxx 来，先选岗位」引导。
- **证据**：`main.js:1834-1835` 深链构造 + `dom/workspace_sel.json`（选择器无简历上下文）+ `format.js` 工作台选择器源码。

### 🟡 中级（P2）

#### P2-1 同一动作多入口且语义不区分（诊断 ×2、导出 ×2、对齐 ×3、投递 ×2）
- **维度**：交互逻辑/UI
- **现状**：简历档案页「诊断简历」「导出 Markdown」各出现 2 次（顶栏 + 诊断卡内），「导出 PDF」2 次（诊断卡 + 完整简历工具条）；工作台「0 条改写建议/0 已采纳/0 待采纳」在头部行与右栏统计各一次；岗位卡每张同时有「去投递↗」「记录投递(工作台)」「工作台」「重新评分」「···」「复选」「状态下拉」。
- **为什么不合理**：入口泛滥导致用户不知道该点哪个、点了会不会重复扣费（诊断/对齐都是 LLM 操作）；「去投递↗」与「记录投递」语义极易混淆（一个外跳、一个写快照）。
- **建议**：① 简历档案页收敛为单一动作条（诊断/导出收进「更多 ▾」）；② 工作台统计数字只保留一处；③ 投递类动作改名：「去投递↗」→「打开招聘页」，「记录投递」→「记录已投递」。
- **证据**：`dom/resume_detail_diag.json`（同标签按钮坐标）、`dom/workspace_job2.json`、`dom/jobs2.json`。

#### P2-2 「添加岗位」内联表单巨型展开造成布局跳变
- **维度**：交互逻辑（反馈）
- **现状**：点击「添加岗位」后，1158×688px 的内联表单在列表中部展开（y=243），列表被整体下推（布局 shift 约 688px），且「批量导入」入口藏在「数据 ▾」菜单里，与「添加岗位」形成两套入口。
- **为什么不合理**：阿泽在点按钮瞬间视口跳变，找不到刚刚看的卡片；对触屏尤其错位。
- **建议**：改为中等宽度模态框（复用现有 showModal），或内联展开时自动滚动到表单顶部并给出收起按钮。
- **证据**：`addjob.py` 探针 BEFORE/AFTER（display:none→block，x=254 y=243 w=1158 h=688）。

#### P2-3 测试数据/内部措辞外泄到正式界面
- **维度**：UI（数据卫生）
- **现状**：① 岗位库存在测试岗位「多行解析验证52200资深后端工程师」（标题自带测试编号）；② 设置页节点名「.env 默认」「omniroute」「nvidia」为内部命名；③ 岗位卡出现「旧版匹配分」「匹配已过期」「待补全」「待分析」等并行状态词，含义重叠；④ 驾驶舱「最近岗位动态」时间显示为 `updated_at`（对齐失败也会刷新它，用户看到「未投递 · 2026-08-25 03:45」会疑惑凌晨发生了什么）。
- **为什么不合理**：老周把测试垃圾当功能理解（「52200 是什么意思」）；内部命名暴露降低专业感；updated_at 冒充「动态时间」产生误导。
- **建议**：① 导出/迁移脚本清理测试岗位（标题含「验证/测试/52200」白名单确认后删除）；② 节点名改为用户可读名或「节点 1/2/3」；③ 「最近岗位动态」改为显示最近快照/投递动作时间（语义化字段），而非 updated_at。
- **证据**：`dom/jobs2.json`（测试标题）、`dom/settings2.json`（节点名）、`dom/dashboard.json`（updated 时间）。

#### P2-4 可访问性基础缺失（触控/aria/焦点）
- **维度**：UI（无障碍）
- **现状**：岗位卡「···」按钮无文本/aria 标签；卡片状态 select 有 aria-label 但 28px 高；「重新评分」「去投递↗」等均为 28px 级按钮；移动端关闭横幅 × 仅 9px；技能缺口按钮无 aria-label。
- **建议**：统一最小触控 40px；菜单按钮补 aria-label（如「岗位更多操作」）；给 has-popup 的按钮加 aria-haspopup；focus-trap 已有（focus-trap.js）但弹窗打开时未确认焦点落点，建议抽查。
- **证据**：`dom/jobs2.json`（按钮坐标 28px）、`dom/mb_workspace.json`（× 9×18px）。

#### P2-5 简历列表信息过载：每卡整份简历全文预览
- **维度**：UI（信息密度）
- **现状**：6 张简历卡，每张 1206×276px，直接渲染整份 Markdown 正文；列表总高 ~1656px。「更新于 2026-08-21 · v1」与「当前版本 v1」重复。
- **为什么不合理**：林然只想挑「哪份简历对应哪个岗位」，卡里却是全文——扫描成本高；6 份同人简历（同名 variant）更是难以区分。
- **建议**：卡片只显示标题/时间/诊断分/版本坏点 + 2 行摘要；全文留给档案页；「当前版本 v1」去掉（卡片头部已显 v）。
- **证据**：`dom/resume_list.json`（每卡 276px、全文文本）。

#### P2-6 设置页节奏与命名问题
- **维度**：UI
- **现状**：六个大区块垂直堆叠（成本护栏/提醒/Token/节点/Guardrails/词表），5 个独立「保存」按钮分散在不同 x（289/1305/2274…），长页面需多次滚动保存；「新增规则」预设 chip（「新增规则 · 拦截外包/单休岗位」）与「新增规则」按钮视觉相似容易误点；Local-ingest Token 明文 + 「复制」按钮孤悬（x=573）。
- **建议**：区块化折叠（每区头部固定保存条）或全区单一「保存并生效」；预设规则与新增按钮分开样式；Token 增加「显示/隐藏」。
- **证据**：`dom/settings2.json`（按钮坐标、Token 明文、规则 chip 文案）。

## 4. Persona 最痛时刻清单（最可能流失/放弃的场景）

按流失概率排序：

1. **【P0-1】点击「继续对齐」→ 等 2 分 46 秒 → 红横幅「模型响应超时，请检查 API Key 与网络」**（Key 明明好的）。林然照做的动作全部无效，第二次尝试前心理预计算：「再失败一次我就换工具」。→ 全站流失点第一。
2. **【P1-1】打开自己最在意的主简历档案页，发现整份简历在预览下面又出现一遍可编辑源码**。对丢数据焦虑型用户 = 「我的简历是不是已经被改动/重复」→ 直接关页去备份（本地工具最怕这个）。
3. **【P1-3】驾驶舱把失败任务标成「待分析/继续对齐」**。第一次是意外，第二次是欺骗；决策台不复决策。
4. **【P0-2】按空态引导「点击右侧顶部『开始优化』」找不到按钮**（按钮叫「开始对齐」且在中间）——次 Persona 阿泽的第一步就迷路。
5. **【P1-4】手机上进工作台，滚 1500px 找不到流程 tabs**；误触 9px 的 ×。
6. **【P1-5】扫技能缺口想补技能，看到一句整段招聘文案**——「这工具是给我做决策的，还是给我念 JD 的？」
7. **【P1-2】老周设置自定义状态后岗位库卡下拉没有**——「设置白改了/系统两套状态」，深度用户弃用往往因为「它不按我说的来」。
